# 草稿层与资产包：解析结果分两层，用户点「入库」才生成固定资产

## Context and Problem Statement

人物 / 地点是**逐章重复抽取**的（第 1 章抽到"贾琏"，第 37 章又抽到"琏二爷"），
所以合并前后根本不是同一份数据：

- **合并前**：每章一条，同一个人有几十条记录，id 形如 `C37-P002`
- **合并后**：一个人一条，但用户还要在这份数据上继续改（改名字、删人、合并两个人）

如果合并完就直接写进最终的 `characters` 表，会引出三个问题：

1. **用户改错了没法回头** —— 删掉的人找不回来，合并的人拆不开
2. **"什么时候算定稿"没有界线** —— 用户改一次算定稿，改十次算哪次？
3. **重跑解析会覆盖用户的手工修改** —— 用户改了半天，一重跑全白费

用户的原话把这条界线画得很清楚：

> 不是 P2/P3 合并了就生成，而是要等 P3 进行完，用户编辑完资产了，**点击入库**了才自动生成 characters 和 locations 表。
> 入库以后就固定资产了，游戏就按照这份固定资产来跑。用户再点一次入库 = 生成新的。

## Decision

### 1. 两层数据，物理分开

| 层 | 表 | 谁写 | 谁读 | 说明 |
|----|----|------|------|------|
| **草稿层** | `characterSnapshots` / `locationSnapshots` | P1 抽 → P2/P3 合并 → **用户编辑** | 资产界面 | 用户改的就是这一层 |
| **资产包（冻结层）** | `characters` / `locations` | **只有「入库」写** | 游戏（只读） | 一份可玩的固定资产 |

`eventLines` 与 `nodes` 只有一份表，但它们的**人物引用**同样分两个阶段：

| 字段 | 草稿阶段 | 入库后 |
|------|---------|--------|
| `nodes.actors` | **人名**（P1 原样，永远不改编成人名之外的东西） | 不变（保持可读） |
| `nodes.actorIds` | 空 | 由代码把 `actors`（含 `targets`）映射成实体 id |
| `eventLines.characterIds` | 空 | 由成员节点的 `actorIds` 汇总 |

### 2. 入库 = 整体重算，不是增量

`publishCanon(bookId)` 每次做完整四步：

```
① 读 characterSnapshots → 重新编号 P001/P002… → 写 characters
② 读 locationSnapshots  → 重新编号 L001/L002… → 写 locations
③ nodes.actors（人名）→ 用相似度映射 → 写 nodes.actorIds
④ eventLines.characterIds ← 成员节点的 actorIds 汇总
```

**关键：草稿层只读不写。** 入库**不**把 `nodes.actors` 改写成 id ——
否则第二次入库就没名字可映射了。想让引用变成 id，看 `actorIds` / `characterIds`。

### 3. id 规则

| 层 | 格式 | 例 | 谁分配 |
|----|------|----|--------|
| P1 快照（人物 / 地点 / 节点**三者同构**） | `C{章号}-{P\|L\|N}{3位序号}` | `C37-P002` | 代码 |
| P2/P3 合并 | **向前合并**：保留最早那条，其余删掉，id 空着不管 | `{C3-P002, C7-P012} → C3-P002` | 代码 |
| 入库后实体 | `P001` / `L001` | `P001` | 代码 |

入库编号顺序**不重要**（用户原话："落库就是打乱了按照重要性随机顺序，编号就好了"）。
本实现按「最早出现的章节」排序，只为**可复现**，不为表达重要性。

### 4. 人名 → id 的映射策略

- 精确匹配（归一化后相等）优先
- 匹配不上再做模糊匹配（互相包含，带单字守卫）
- **模糊命中多个候选时宁可不认**，返回 `undefined` 并记进 `unmappedNames`
- 映射结果只写 `actorIds` / `characterIds`，**不改 `actors`**

### 5. 重跑与覆盖

- P2/P3 重跑：覆盖草稿层（用户的手工编辑会丢，这是已知代价）
- **入库**：覆盖资产包，用当前草稿生成新的一份
- 用户删掉一条快照 → 下次入库那个人的 id 就空出来，**不重排已入库的其他人**
  （重排会让游戏里已有的引用失效）

## Consequences

- **好的**：用户有明确的"定稿"动作，改错了可以继续改草稿、重新入库。
- **好的**：游戏只读一份固定资产，运行时数据与解析数据彻底解耦，不会互相污染。
- **好的**：`nodes.actors` 保留人名，UI 与 Prompt 都不需要为了显示"谁参与了"去查人物表（避免 N+1）。
- **好的**：id 不带 `bookId` 前缀也安全（每本书一个库，见 ADR-002）。
- **坏的**：多占一份存储（快照 + 实体）。长篇小说几十 MB 量级，IndexedDB 无压力。
- **坏的**：入库是一次全量写入，人物 / 地点上千条时会有短暂卡顿（MVP 可接受）。
- **风险**：P2/P3 重跑会覆盖用户的手工编辑。**缓解**：入库前先确认；后续可加"合并前提示有手工编辑"。

## Implementation Plan

- **Affected paths**：
  - `app/src/core/schema/character-snapshot.ts`（草稿层 schema）
  - `app/src/core/schema/character.ts` / `location-snapshot.ts`（资产包 schema）
  - `app/src/core/pipeline/run-merge.ts`（合并 → **写回快照表**）
  - `app/src/core/pipeline/publish.ts`（**入库**，本 ADR 的核心）
  - `app/src/core/assets/edit.ts`（所有编辑函数都在快照层，且必须传 `bookId`）
  - `app/src/queries/index.ts`（`useCharacterSnapshots` = 草稿；`useCharacters` = 资产包）
  - `app/src/features/assets/`（资产页读快照表 + 「入库」按钮）
- **Patterns to follow**：
  - **代码分配 id**，模型永不产出 id（ADR-003 的工程约定）
  - 入库**只读**草稿表、**只写** `characters` / `locations` / `nodes.actorIds` / `eventLines.characterIds`
  - 所有写入走 `core/` 里的封装函数，UI 不直接碰表
  - 合并与入库都要**幂等**：同一份草稿跑两次，结果一样
- **Patterns to avoid**：
  - ❌ 不要在 P2/P3 里写 `characters` / `locations`
  - ❌ 不要把 `nodes.actors` 改写成 id
  - ❌ 不要在 UI 里读 `characters` 来显示"待编辑的人物"（那是草稿层的活）

### Verification

- [x] 合并结果写回快照表，`characters` / `locations` 保持为空（`tests/run-merge.test.ts`）
- [x] 入库后 id 是 `P001` / `L001`，且按最早章节可复现（`tests/publish.test.ts`）
- [x] `nodes.actors` 保持人名，`actorIds` 是映射出的 id
- [x] `eventLines.characterIds` 在**同一次入库**里从成员节点汇总出来
- [x] 连点两次入库不会翻倍（整体重算）
- [x] 没匹配上的名字会被报出来（不静默丢）
- [x] 资产界面入库前读快照表、显示「未入库 / 资产包」状态（e2e）
- [ ] 用户手工编辑后再入库，资产包反映最新草稿（手工验证）

## Alternatives Considered

- **合并完直接写 `characters`，用户在这张表上改**：省一层表，但"重跑解析"与"用户手工修改"会互相覆盖，且删人不可撤销 —— 用户明确否决。
- **被合并的实体加 `mergedInto` 标记、不删除（可撤销）**：这是早期方案，已废弃。用户改成"**向前合并、其余删掉、id 空着不管**"：简单、不留悬空引用。
- **`nodes.actors` 直接改写成 id**：检索方便，但①原文称呼丢失 ②第二次入库无法重新映射 ③UI 要回查人物表才能显示人名。改为保留 `actors` + 新增 `actorIds`。
- **入库时保留快照 id 作为实体 id（`C3-P002`）**：不用映射，但 id 冗长、且暴露"第几章抽到"这种用户不关心的实现细节；用户明确要求重新编码成 `P001`。

## More Information

**什么情况下该重新考虑**：

- 若用户频繁"改一点 → 入库"导致资产包反复整体重写变慢 → 改成增量 diff 更新
- 若出现"同一份草稿要生成多份并行资产包"的需求 → 资产包要带自己的 id（`pkg001`），不能只有一张表
- 若 P2/P3 重跑覆盖手工编辑成为高频痛点 → 引入草稿的本地编辑日志（patch 层）
