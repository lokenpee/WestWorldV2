# 并发、限流、重试与降级策略

## Context and Problem Statement

P1 要对一本上千章的小说跑上千次模型调用（每章 2 次）。这个规模下，**限流与失败是常态，不是异常**：

- 供应商会返回 429（限流）
- 网络会抖
- 结构化输出会偶尔不符合 schema
- Key 可能配错

**没有明确的重试与降级策略，会出现两种坏结果**：要么一遇错就整个任务崩掉（跑了几十分钟白跑），要么无限重试烧钱。

另外 ADR-006 的浏览器 Spike 已经发现：**`pi-ai` 的模型调用失败不抛异常**，而是返回 `stopReason: 'error'`。重试逻辑必须建立在这个事实上。

## Decision

### 1. 并发

**默认 3，可配置**（用户已定）。

选 3 的理由：串行跑 1200 章太慢；并发太高会更快撞到供应商的限流阈值。3 是一个保守的起点，实测后再调。

**所有并发走同一个全局并发控制器**，各阶段不各自开池。

### 2. 错误分类与重试策略

**前提**：因为 `pi-ai` 不抛异常，判定错误类型必须解析 `res.stopReason` 与 `res.errorMessage`：

```typescript
const res = await models.complete(...);
if (res.stopReason === 'error') {
  const kind = classifyError(res.errorMessage);   // ← 集中在一处实现
  // ...
}
```

| 错误类型 | 判定依据 | 重试 | 次数 | 退避 |
|---------|---------|------|------|------|
| 网络错误 | fetch 失败 / 无 HTTP 状态 | ✅ | 3 | 1s → 2s → 4s（+ 抖动） |
| 限流 429 | `errorMessage` 含 429 | ✅ | 5 | **尊重 `Retry-After`**，无则指数退避 |
| 服务端 5xx | 500–599 | ✅ | 3 | 指数退避 |
| 认证 401/403 | 401 / 403 | ❌ | — | **中止整个编译任务**（用户必须去改 Key） |
| 结构化输出不合法 | TypeBox 校验失败 | ✅ | 2 | 立即重试，**把校验错误回传给模型** |
| 内容被拒 | 供应商的内容策略 | ❌ | — | 标记该章失败 |
| 上下文超长 | context length 相关 | ❌ | — | 标记该章失败（记录原因） |

**抖动（jitter）必须有** —— 并发 3 个请求同时失败时，不加抖动会同时重试，再次撞墙。

### 3. 降级：重试耗尽后怎么办

| 场景 | 行为 |
|------|------|
| **单章失败**（重试耗尽） | 标记该章 `failed`，**跳过，继续下一章**（⚠️ 待确认是否改成中止） |
| **整个任务** | 不中止，继续跑完其余章节 |
| **编译结束** | 给出失败章节列表，用户可单独重跑 |
| **认证失败（401/403）** | ⚠️ **例外**：这是配置问题不是偶发问题，**中止整个任务**并提示用户检查 Key |

**理由**：跑了几十分钟的任务，不应该因为某一章失败而全部丢弃。用户可以选择事后重跑失败的章节。

### 4. 成本护栏：不做（但预留扩展点）

**已确认：MVP 阶段不设成本护栏。** 当前目标是**可行性验证**，账户余额本身就是护栏。

**但必须预留扩展点** —— 一个配置错误（误用很贵的模型、提示词 bug 导致重试风暴）仍可能快速烧钱：

- 累计费用已在**实时统计**（ADR-010），所以做护栏所需的数据是现成的
- 扩展点位置：`app/src/core/pipeline/runner.ts` 的任务循环里，每章完成后检查一次累计费用
- 将来加护栏时只需在这个检查点插入「暂停 + 询问」，**不需要改动架构**

### 5. Agent 内部的工具调用并发

P2 / P3 的 Agent run 里，一次可能返回多个 tool_call。**用 `pi-agent-core` 的 `sequential` 模式**（默认），不用 `parallel`。

理由：这些工具（`query_nodes` / `read_original`）读的是同一批数据，并发没有收益，反而让工具调用记录难以阅读。

## Consequences

- **好的**：错误分类集中在一处，各阶段不各自判断。
- **好的**：单章失败不影响整体，跑几十分钟的成果不会因为一章丢失。
- **好的**：认证错误快速失败，不浪费重试。
- **坏的**：跳过失败章节意味着"编译完成"不等于"全部章节都成功" —— UI 上必须把失败数**显著地**展示出来，否则用户会以为全都好了。
- **风险**：重试次数 × 并发数 × 章节数 = 最坏情况下的调用量。**当前没有成本护栏**，只能靠 ADR-010 的实时费用显示让用户自己察觉；护栏扩展点已预留。

## Implementation Plan

- **Affected paths**：`app/src/core/llm/errors.ts`（`classifyError`）、`app/src/core/llm/retry.ts`（带退避的重试包装）、`app/src/core/pipeline/runner.ts`（并发池，与 ADR-008 同一处）
- **Dependencies**：无新增
- **Patterns to follow**：
  - 所有模型调用统一走 `withRetry(fn, policy)`，不在各阶段写重试
  - `classifyError` 是唯一判定错误类型的地方
  - 退避必须带抖动：`delay = base * 2^attempt * (0.5 + Math.random())`
- **Patterns to avoid**：
  - ❌ 不要用 try/catch 判定模型调用失败（`pi-ai` 不抛异常，见 ADR-006）
  - ❌ 不要在重试里忽略 `Retry-After`
  - ❌ 不要让各阶段自定义重试次数

### Verification

- [ ] 用假 Key 触发 401，验证任务**立即中止**并提示检查 Key（不重试）
- [ ] 人为返回 429 并带 `Retry-After`，验证重试尊重该值
- [ ] 人为让 3 个并发请求同时失败，验证重试时间被抖动打散（不是同时重试）
- [ ] 结构化输出校验失败时，验证错误信息被回传给模型并重试
- [ ] 单章重试耗尽后被标记 `failed`，其余章节继续跑完
- [ ] 编译结束后的报告里能看到失败章节列表

## Alternatives Considered

- **失败即中止整个任务**：实现简单，但跑几十分钟后因为一章失败而全丢，对用户不可接受。
- **无限重试**：会烧钱，且遇到认证错误会永久卡住。
- **固定的重试间隔（无抖动）**：并发场景下会导致重试风暴。
- **并发设得更高（如 10）**：更快，但更容易触发供应商限流，实际吞吐可能反而更低。

## More Information

**什么情况下该重新考虑**：

- 若实测 3 并发仍频繁触发 429 → 降到 1–2，或引入自适应并发（根据 429 比例动态调整）
- 若失败章节比例很高（>10%）→ 说明提示词或模型选型有问题，应从根因解决而不是靠重试
- 若将来要加成本护栏 → 扩展点已留在任务循环里，数据来自 ADR-010，不需要改动架构
