# M1 · 解析资产 — 实施计划

> **目标**：导入 `.txt` → 分章 → P1 提取 → 得到结构化的**世界资产**（人物 / 地点）与**叙事资产**（事件节点）→ 落库 → 能在界面上看到。
> **范围**：P1 + 数据层 + 最小预览。
> **明确不做**（留到下一轮）：P2 事件线聚合、P3 全局人物合并、时间轴推断、事件网络地图。
> 依据：PRD v1.0 + ADR-001~014 + `docs/engineering-conventions.md`

---

## 为什么先做这一段

P1 是整条链路里**唯一读原文**的一步，也是**最大的技术风险**：

- 分章正则能不能吃下真实的网文 txt？
- 提示词能不能抽出稳定、可校验的结构化数据？
- pi-ai 的结构化输出在这套 schema 上稳不稳？

这三件事任何一件不成立，后面 P2/P3 做得再漂亮都没用。**所以先把 P1 打通，用真实小说验证。**

### 步骤 1 · TypeBox Schema 层 ✅ 已完成（2026-10-03）

**产出**：`app/src/core/schema/` 下的三个 schema

| 文件 | 内容 |
|------|------|
| `character-snapshot.ts` | 人物快照（P1 产出，不判层级） |
| `location.ts` | 地点 |
| `node.ts` | 事件节点 |
| `extraction.ts` | P1 两次调用的输出容器（`{chapter_index, chapter_name, characters[], locations[]}` / `{chapter_index, chapter_name, nodes[]}`） |

**规则**（ADR-003）：

- 每个字段必须写 `description`（中文，面向模型）
- 类型导出用 `Static<typeof X>`
- 运行时校验用 `TypeCompiler.Compile(X)`
- **不引入 Zod**

**验证**：Vitest 用一份手写的样例 JSON 跑 `safeParse` 成功；故意删一个必填字段，校验失败。

### 步骤 6 · P1 单章提取（核心）

**产出**：`app/src/core/pipeline/p1.ts`

```
extractChapter(chapter, ctx)：
  ① 调用 01-extract-world-assets  → characters[] + locations[]
  ② 调用 02-extract-narrative-assets → nodes[]
  ③ 两次结果都过 TypeBox 校验
  ④ 代码分配 id（C037-P01 / C037-N01 …）—— LLM 不产出 id
  ⑤ 返回结构化结果
```

**验证**：**拿真实小说的一章**跑一次，人工检查：
- 人物是否漏抽/多抽
- 事件节点是否"在记录"而不是"在解释"
- 有没有把一段里的多个事实合成一个节点

> 这是整个计划里**唯一需要人工判断质量**的一步。前面所有步骤都是机械可验证的。

## 执行顺序的理由

```
0 脚手架
   ↓
1 Schema  ← 先定数据形状
   ↓
2 数据层  ← 表结构要对齐 schema
   ↓
3 分章    ← 纯代码，无依赖，最快能验证，也是 P1 的输入
   ↓
4 模型层  ← P1 依赖它
   ↓
5 提示词渲染 ← P1 的输入
   ↓
6 P1 提取 ← 核心
   ↓
7 落库 → 8 预览
```

**3 和 4 可以并行**（互不依赖）。

---

## 本轮结束的判定标准

| # | 标准 |
|---|------|
| 1 | 导入一本真实的中文小说 txt，能正确分章（≥95% 章节边界正确） |
| 2 | 对任意一章跑 P1，产出通过 TypeBox 校验的结构化数据 |
| 3 | 数据落进 IndexedDB，刷新后仍在 |
| 4 | 界面上能看到人物 / 地点 / 节点列表 |
| 5 | 每个节点都能看到它的原文出处（`quote`） |
| 6 | 全程 `core/` 里没有 React / DOM 依赖（`pnpm lint` 通过） |

**达到这 6 条，"解析资产"这一段就算跑通了**，可以进 P2（事件线聚合）。
