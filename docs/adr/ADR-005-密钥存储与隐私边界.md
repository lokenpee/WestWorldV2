# 纯浏览器环境下：API Key 明文存 IndexedDB + 四条纪律

> **本 ADR 已根据 ADR-001（纯浏览器）重写并确认。**
> 原方案是"存入系统钥匙串"，但那依赖桌面外壳 —— 本项目的运行形态是纯浏览器，没有系统钥匙串。
> **决策结果（2026-10-03）：采用方案 A —— 明文存 IndexedDB，并遵守下面四条纪律。**

## Context and Problem Statement

两个必须解决的问题：

**① API Key 存哪里。** 纯浏览器环境下没有系统钥匙串，可选位置只有 `localStorage` / `IndexedDB` / `sessionStorage`。前两者都是**明文**，本地任何脚本、浏览器扩展都能读。

**② "数据不出本机"这句话不准确。** 每次调模型，章节正文必须发送给模型服务商。这句话字面上是错的。

**已知约束**（来自用户）：

- 模型请求**从前端发**（浏览器直连）
- API Key **不写进代码**，存在本地配置里
- 工具是**个人自用**，不是公开分发

## 候选方案

| 方案 | 安全性 | 体验 | 说明 |
|------|-------|------|------|
| **A. IndexedDB 明文存储** | 低 | 最好 | 一次配置永久生效；本地脚本/扩展可读 |
| **B. 只存 sessionStorage** | 中 | 差 | 关标签页就丢，每次开应用要重填 |
| **C. 用户口令派生密钥加密后存 IndexedDB** | 中高 | 中 | 每次启动输一次口令解锁；口令忘了 Key 就找不回来 |
| **D. 不存，每次编译前手输** | 高 | 差 | 一个跑几十分钟的任务中途可能被打断 |

## 决策结果

**方案 A：明文存 IndexedDB**，并遵守四条纪律：① 导出备份不含 Key ② 日志不含 Key ③ UI 打码只显示后 4 位 ④ 设置页明确告知"明文存储、仅建议本机个人使用"。

## 我的建议

**选 A（明文存 IndexedDB），但必须配四条纪律**：

1. **不导出**：备份 / 导出功能默认**不包含** Key
2. **不打日志**：日志、错误信息、崩溃报告里绝不出现 Key
3. **UI 打码**：设置页里 Key 只显示后 4 位
4. **明确告知**：设置页写清"Key 以明文存在浏览器本地，仅建议在这台个人电脑上使用"

理由：威胁模型上，这是**个人自用、本机运行**的工具。真实风险主要是"本机的恶意扩展 / 脚本"，而 C 方案（口令加密）对个人工具来说**每次启动都要输口令**的摩擦过高，收益不成正比。

**若将来要分发给别人用，必须升级到 C 或换回桌面外壳用系统钥匙串。**

## Consequences

- **好的（选 A）**：零摩擦，配置一次永久生效。
- **坏的（选 A）**：本机恶意脚本 / 浏览器扩展可读取 Key。
- **坏的**：换浏览器或清浏览器数据会丢 Key（与 ADR-001 的数据持久性风险同源）。

## Implementation Plan

- **Affected paths**：`app/src/core/config/credential-store.ts`（实现 pi-ai 的 `CredentialStore` 接口）、`app/src/features/settings/`、`app/src/core/export/`
- **Patterns to follow**：
  - **实现 pi-ai 的 CredentialStore 接口**（ead / list / modify / delete）并注入 createModels({ credentials })，这样 Key 的读写由 PI 统一走这个接口（见 ADR-004）
  - 业务代码不直接碰 IndexedDB 里的凭据表
  - 日志脱敏：请求正文只记长度与章节号，不记内容与 Key
  - 导出逻辑里显式排除 Key 字段
- **Patterns to avoid**：
  - ❌ 不要把 Key 写进代码库、`.env`、测试 fixture
  - ❌ 不要绕过 `CredentialStore` 直接读写凭据表
  - ❌ 不要在日志 / 报错里包含 Key 或章节正文
  - ❌ 不要在导出备份里带上 Key
