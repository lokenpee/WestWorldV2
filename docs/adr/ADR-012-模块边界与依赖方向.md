# 分层模块边界与单向依赖，用 ESLint 机器强制

## Context and Problem Statement

项目会长大（P1/P2/P3 + Agent + 工具 + 事件 + UI）。**没有强制的边界，最终一定是一团**：

- UI 组件直接调 IndexedDB，换个界面就要重写业务逻辑
- `core` 里 `import React`，导致业务逻辑没法单测、没法搬进 Worker
- 工具层直接写库，绕过了 ADR-006 的"Agent 不写库"约定

**靠自觉守不住边界** —— 必须是机器强制。

## Decision

### 1. 分层

```
L6  features/         UI（React）—— 只能向下依赖
L5  workers/          可选的任务宿主
L4  pipeline/         阶段编排（P1 / P2 / P3）
L3  agent/  events/   Agent 运行时 + 事件总线
L2  llm/  tools/      模型调用 + 工具定义
L1  db/               Dexie 数据层
L0  schema/ shared/   TypeBox 定义 + 纯工具
```

### 2. 四组硬规则

| # | 规则 | 为什么 |
|---|------|--------|
| 1 | **`core/` 下的任何东西都不能 import `features/`** | 业务逻辑不能依赖 UI |
| 2 | **`core/` 下不能 import React / 任何 DOM API**（`window` / `document` / `localStorage`） | 保证可单测、可搬进 Worker（ADR-008 的前提） |
| 3 | **`features/` 不能直接 import `db/` 或 `llm/`** | UI 只能通过 `core/` 暴露的能力做事 |
| 4 | **`tools/` 不能写库**（不能 import `db` 的写方法） | ADR-006 的"Agent 永不直接写库" |

### 3. 用 ESLint 机器强制

**不是写在文档里靠自觉，而是让 `pnpm lint` 直接报错。**

```javascript
// eslint.config.js（示意）
{
  files: ['app/src/core/**/*.ts'],
  rules: {
    'no-restricted-imports': ['error', {
      patterns: [
        { group: ['**/features/**'], message: 'core 不能依赖 features（ADR-012）' },
        { group: ['react', 'react-dom'], message: 'core 不能依赖 React（ADR-012）' },
      ],
    }],
    'no-restricted-globals': ['error',
      { name: 'window', message: 'core 不能碰 DOM（ADR-012）' },
      { name: 'document', message: 'core 不能碰 DOM（ADR-012）' },
    ],
  },
}
```

**`pnpm lint` 必须进 CI / 提交前钩子。**

### 4. 允许的依赖方向（唯一合法路径）

```
features/ ──→ core/pipeline ──→ core/agent ──→ core/tools ──→ core/db
                   │                 │              │           │
                   └─────────────────┴──────────────┴───────────┘
                                     ↓
                                 core/schema
```

**跨层只能向下，不能向上，不能横向绕行**（如 `db` 直接 import `llm`）。

## Consequences

- **好的**：业务逻辑与 UI 彻底解耦，可以单测、可以搬进 Worker（ADR-008 预留的路径因此才成立）。
- **好的**：违反边界时 `pnpm lint` 直接报错，不依赖人的记性。
- **好的**：`features/` 不能直接碰 `db`，天然防止"UI 里写业务逻辑"这个最常见的腐化方式。
- **坏的**：多一层 ESLint 配置要维护；某些"图方便"的直连写法会被拦下来，需要多写一层转发函数。
- **风险**：过度分层也会带来样板代码。如果某个转发函数只是纯透传、没有任何逻辑，可以考虑放宽（但**第 1、2、4 条不能放宽**）。

## Implementation Plan

- **Affected paths**：`app/eslint.config.js`（分层规则）、`app/src/` 的目录结构、`app/package.json`（`lint` 脚本）
- **Dependencies**：`eslint`、`typescript-eslint`
- **Patterns to follow**：
  - 所有跨层调用都经过明确的模块导出（`core/pipeline/index.ts` 这类 barrel）
  - 需要 DOM 的地方（如导出下载文件）放在 `features/`，由它调用 `core/` 拿到数据
- **Patterns to avoid**：
  - ❌ `core/` 里 `import React` 或 `document.createElement`
  - ❌ `features/` 里 `import { db } from '../core/db'`
  - ❌ `tools/` 里 `db.nodes.put(...)`（写操作必须在 pipeline 层）

### Verification

- [ ] 在 `core/` 里故意 `import React`，`pnpm lint` 报错
- [ ] 在 `core/` 里故意使用 `window`，`pnpm lint` 报错
- [ ] 在 `features/` 里故意 `import` `core/db`，`pnpm lint` 报错
- [ ] 在 `tools/` 里故意调用写库方法，`pnpm lint` 报错（或 code review + 测试拦截）
- [ ] 全仓库搜索：`app/src/core/` 下不存在 `react` / `window.` / `document.`
- [ ] `pnpm lint` 已接入提交前钩子或 CI

## Alternatives Considered

- **只写文档约定，靠自觉**：项目一大必然失守。
- **用 Nx / Turborepo 之类的 monorepo 工具约束边界**：对单人项目过重，ESLint 规则足够。
- **不做分层，按功能切目录**：小项目可以，但这个项目 core 逻辑明显要独立于 UI（要能搬进 Worker），分层是必需的。
- **依赖注入框架**：过重，直接 import 单向依赖就够。

## More Information

**什么情况下该重新考虑**：

- 若某个规则导致大量无意义的透传样板 → 评估是否放宽（但第 1、2、4 条不放宽）
- 若引入 Worker → `workers/` 的依赖规则要单独定义（它应能依赖 `core/`，但不能依赖 `features/`）

相关：ADR-008（pipeline DOM-free 是搬 Worker 的前提）、ADR-006（Agent 不写库）、ADR-003（schema 层）
