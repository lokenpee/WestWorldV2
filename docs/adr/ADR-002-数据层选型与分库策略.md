# 采用 Dexie 作为 IndexedDB 封装层，并采用「每本书一个 Canon 库 + 每世界线一库」的分库策略

## Context and Problem Statement

存储引擎已定为 IndexedDB（PRD 2.1），原因：本地工具、零配置、容量大、支持索引。但直接用原生 API 有三个具体痛点：

1. API 是事件 / 回调式的，复杂查询要手写游标。本项目需要大量索引查询（`chapterIndex`、`name`、`order`）。
2. **版本迁移（`onupgradeneeded`）手写极易写错，写错就丢用户已编译的数据** —— 而本项目的 schema 已经改过很多轮，未来还会改。
3. 节点 ↔ 事件线是**多对多**，需要 `multiEntry` 索引，原生写法冗长。

另外 PRD 2.8 已确定分库策略的**需求**（Canon 不可变、多条世界线物理隔离），但没定怎么落地。

## Decision

**采用 Dexie.js 作为 IndexedDB 封装层**，并采用如下分库策略：

```
westworld_settings                 ← 设置库：凭据 / 应用设置 / **书架（books）**
westworld_canon_{bookId}           ← Canon 库：**每本书一个**，装这本书的编译产物
westworld_state_{bookId}_{lineId}  ← 世界线库：每条世界线一个，物理隔离
```

> **修正（2026-10-04）**：早期版本写的是"单个 Canon 库，靠记录里的 `bookId` 字段区分"。
> 实测证明这条行不通：**id 是书内编号**（`C3-P002` / `C37-N001` / 入库后的 `P001`），
> 两本书都会有自己的"第 1 章""第 3 个人物"，共用一个库就会**互相覆盖**（这个 bug 真实发生过，
> 现在有回归测试兜着：`tests/db.test.ts` 的「每本书一个库」用例）。
>
> 所以改成**每本书一个 Canon 库**，id 天然按书隔离，不需要给每个 id 加前缀。
> 记录里的 `bookId` 字段保留，但只是**冗余的自描述信息**（导出、调试时方便）。
>
> 书架（"用户导入过哪些书"）是**跨书全局信息**，放不进任何单本书的库，因此搬到设置库。

**Non-goals（明确不做）**：

- 不引入 SQLite / DuckDB / 图数据库（规模不够，见 PRD 2.7）
- 不做跨世界线的联合查询 UI（低频操作，需要时逐个开库即可）
- 不让业务代码直接使用原生 IndexedDB API

## Consequences

- **好的**：声明式迁移（`db.version(n).stores({...})`），schema 演进时不容易丢数据。
- **好的**：Dexie 是**薄封装** —— 底层仍是标准 IndexedDB，对象仓库与索引格式不变，必要时可降级回原生 API 而不丢数据。
- **好的**：**书与书之间物理隔离**，不存在"漏过滤 `bookId` 导致串味"这一类 bug。
- **好的**：删一本书 = 删一个库（`deleteCanonDb(bookId)`），干净彻底。
- **坏的**：引入一个第三方依赖（约 80 KB）。
- **坏的**：书架要跨库读（设置库里列书 → 逐本开库），导出 / 导入要同时处理两个库。
- **风险**：Dexie 的 `multiEntry` 索引在半结构化数组数据上（节点 id 数组）行为需要实测确认。

## Implementation Plan

- **Affected paths**：`app/src/core/db/`（`stores.ts` 表结构、`canon.ts` 每本书一个库、`settings.ts` 设置库、`repo.ts` 读写封装）、`app/src/core/schema/`（TypeBox schema 是业务数据的唯一真相源）
- **Dependencies**：`dexie`、`dexie-react-hooks`（UI 层响应式查询用）
- **Patterns to follow**：
  - 每类数据库一个模块：`db/canon.ts`、`db/settings.ts`；表结构集中声明在 `db/stores.ts`，不要在业务代码里散落表名
  - 取库统一走 `getCanonDb(bookId)` / `getSettingsDb()`，**不要**在业务代码里 `new Dexie(...)`
  - 索引按 `CANON_STORES` / `SETTINGS_STORES` 声明；**改了 schema 就要同步改索引**（有漂移测试 `tests/db.test.ts`）
  - UI 只通过 `src/queries/` 订阅（`useLiveQuery`）
- **Patterns to avoid**：
  - ❌ 不要在业务逻辑里直接写 `indexedDB.open()`
  - ❌ 不要用字符串拼接查询
  - ❌ 不要在没有迁移声明的情况下改表结构

### Verification

- [x] 能创建 Canon 库并建出 `CANON_STORES` 清单里的全部对象仓库与索引（漂移测试覆盖）
- [x] **两本书都有"第 1 章"的快照，不会互相覆盖**（`tests/db.test.ts`）
- [x] 书架（`books`）在设置库里，与 Canon 库物理隔离
- [x] 单本书的完整编译数据写入后，重启应用数据完整
- [ ] 用一个模拟的 schema 变更验证迁移：旧数据保留，新索引可用
- [ ] 库名包含 `bookId` / `lineId`，同一本书的两条世界线互不可见

## Alternatives Considered

- **原生 IndexedDB**：零依赖，但迁移手写易错，且本项目 schema 会反复演进 —— 这个风险直接对应"丢用户几十分钟的编译成果"。
- **`idb`（Jake Archibald）**：提供了 Promise 化，但**没有解决迁移手写的问题**，等于只解决了一半痛点。
- **SQLite（WASM / sql.js）**：与已确定的"IndexedDB 存结构化数据"冲突；WASM 版的持久化还要自己落盘。
- **单库 + `bookId` 字段过滤**：跨书查询方便，但 id 是书内编号，必然冲突（实测已复现）—— 只能靠给 id 加 `bookId` 前缀绕开，那是把复杂度摊到每一条数据上。
- **图数据库（Kuzu / Neo4j）**：见 PRD 2.7，本项目的图规模在内存里就能跑。

## More Information

**什么情况下该重新考虑**：

- 若单本书编译后的数据超过 **1 GB** → IndexedDB 可能吃力，需评估分片或迁移到 SQLite
- 若浏览器对"应用创建的数据库数量"有限制（Chrome 对每个 origin 的库数量有上限）→ 需要把老旧的书归档 / 合并
- 若 Dexie 出现无法绕过的 bug → 降级到 `idb` 或原生 API（数据格式兼容，可平滑迁移）
