# Dexie 版本化迁移，且区分「可重生成数据」与「不可重生成数据」

## Context and Problem Statement

本项目的 schema **已经改过很多轮**（人物字段、节点字段、事件线字段、时间轴……），未来还会改。

用户电脑上已经存在编译好的数据。**改 schema 时如果不管旧数据，用户打开应用就会崩或者看到错乱的数据。**

同时，IndexedDB 的迁移（`onupgradeneeded`）**写错就丢数据** —— 这正是 ADR-002 选择 Dexie 的原因之一。

## Decision

### 1. 一切 schema 变更都走 Dexie 版本化迁移

```typescript
// app/src/core/db/canon.ts
db.version(1).stores({ characters: 'id, name, roleWeight', nodes: 'id, chapter_index' });

db.version(2)
  .stores({ characters: 'id, name, roleWeight, aliases', nodes: 'id, chapter_index, time_coord' })
  .upgrade(tx => tx.table('characters').toCollection().modify(c => { c.aliases ??= []; }));
```

**规则**：每次改动 `stores()` 声明或数据结构 → **版本号 +1 + 写 upgrade 函数**。不允许"改了声明不升版本"。

### 2. 哪些变更需要迁移

| 变更 | 需要 upgrade 函数吗 |
|------|-------------------|
| 新增字段（有默认值） | 通常不需要（读取时兜底），但显式补上更安全 |
| 新增字段（无默认值） | ✅ 需要 |
| 删除字段 | ✅ 需要（清理） |
| 重命名字段 | ✅ 需要 |
| 改字段类型 / 结构 | ✅ 需要 |
| **新增 / 删除索引** | ✅ 需要（`stores()` 声明变化即触发版本升级） |

### 3. ⭐ 区分两类数据（这是本 ADR 最重要的判断）

```
可重生成数据（Canon 层）           不可重生成数据（世界线层）
  · 人物实体                          · 玩家做过的选择
  · 地点                              · 世界状态
  · 事件节点                          · 变更账本
  · 事件线                            · 快照
  · 时间轴
  · 原文
       ↓                                    ↓
  重新跑一次 P1/P2/P3 就有              丢了就真的没了
```

**迁移策略按类型区分**：

| 数据类型 | 迁移失败时 |
|---------|-----------|
| **可重生成**（编译产物） | 提示用户**「重新编译」** —— 比重磕一个复杂的迁移函数更可靠，代码也更简单 |
| **不可重生成**（世界线） | **必须成功**。失败则**保留原始数据不删**，阻止加载并提示用户从备份恢复 |

**为什么这个区分重要**：它让"迁移"这件事的风险大幅下降。编译数据本来就是从小说生成的，重新生成是**确定性**的（同样的输入 → 同样的中间产物），而一个写错的迁移函数是**不可逆**的。

> ⚠️ 注意：重新编译会**再次消耗 API 费用**。所以迁移失败时，UI 上要同时给出「尝试修复」和「重新编译」两个选项，并标注后者会产生费用。

### 4. 迁移必须可测

每个迁移配一个测试：

```
准备：用 v(n-1) 的 schema 写入样例数据
执行：打开 v(n) 的数据库（触发 upgrade）
断言：新结构正确、旧数据没丢、新字段有合理默认值
```

**没有测试的迁移等于没写迁移。**

### 5. 迁移失败的兜底

**绝不静默丢数据**：

- 捕获迁移异常 → **不删除原始数据库**（Dexie 会保留）
- 阻止应用进入正常流程，显示明确的错误页：

```
数据升级失败
原因：……
你的原始数据仍然保留在本机，没有被删除。

[重试]  [从备份恢复]  [重新编译（会消耗 API 费用）]  [导出原始数据]
```

**`[导出原始数据]` 这一项很重要** —— 即使升级失败，也要让用户能把数据抢救出来。

## Consequences

- **好的**：schema 可以放心演进，不用怕旧数据。
- **好的**：区分两类数据后，编译产物的迁移可以"降级为重跑"，大幅降低迁移代码的复杂度与风险。
- **好的**：迁移失败不会丢数据，且有多个出路。
- **坏的**：每个版本要写迁移函数 + 测试，有持续的维护成本。
- **坏的**：用户可能被要求"重新编译"（要花钱），这需要明确告知。
- **风险**：连续多个版本的迁移链（v1→v2→v3→v4）可能组合爆炸。缓解：**只支持从"最近 3 个版本"迁移**，更旧的版本提示用户从备份恢复或整体重编译。

## Implementation Plan

- **Affected paths**：`app/src/core/db/migrations/`（每个版本一个文件）、`app/src/core/db/canon.ts`、`app/src/core/db/worldline.ts`、`app/tests/migrations/`、`app/src/features/error/`（迁移失败页）
- **Dependencies**：无新增（Dexie 内置版本机制）
- **Patterns to follow**：
  - 每个版本的迁移一个文件：`v2-add-aliases.ts`，导出 `upgrade(tx)` 与描述
  - 迁移函数只做数据搬运，不调用业务逻辑（避免依赖变化导致迁移失败）
  - 迁移测试用真实的旧版本数据样本
- **Patterns to avoid**：
  - ❌ 不要在迁移函数里调用 `core/` 的其他模块（迁移应该是最稳定的代码）
  - ❌ 不要在迁移失败时删除数据库
  - ❌ 不要"改了 schema 不升版本"

### Verification

- [ ] 有一个可运行的迁移测试：写入 v(n-1) 数据 → 打开 v(n) → 断言新结构正确
- [ ] 手动让迁移函数抛错，验证：原始数据仍在、显示错误页、能导出原始数据
- [ ] 迁移失败后选择「重新编译」，能正常从原文重跑（原文未被删除）
- [ ] 世界线数据的迁移失败时，不会删除任何东西
- [ ] 从 v1 数据直接升到最新版本（跨越多个版本）能成功

## Alternatives Considered

- **不做迁移，改 schema 就清库**：用户几十分钟的编译成果全丢，不可接受。
- **用原生 `onupgradeneeded`**：ADR-002 已分析，手写迁移容易丢数据，所以选 Dexie。
- **所有数据都要求迁移成功**：对编译产物来说是不必要的风险与工作量 —— 它本来就能重新生成。
- **所有数据都靠重新生成**：世界线数据（玩家的选择与状态）丢了就真的没了，不能这样处理。
- **支持从任意旧版本迁移**：迁移链组合爆炸。改为只支持最近 3 个版本。

## More Information

**什么情况下该重新考虑**：

- 若迁移测试维护成本过高 → 简化策略：编译产物一律"重新编译"，只对世界线数据写迁移
- 若用户量增长（不再只是个人自用）→ 需要更严谨的迁移回归测试与灰度策略
