# 采用 Dexie 作为 IndexedDB 封装层，并采用「Canon 库 + 每世界线一库」的分库策略

## Context and Problem Statement

存储引擎已定为 IndexedDB（PRD 2.1），原因：本地工具、零配置、容量大、支持索引。但直接用原生 API 有三个具体痛点：

1. API 是事件 / 回调式的，复杂查询要手写游标。本项目需要大量索引查询（`by_chapter`、`by_time`、`by_actor`、`by_event_line`）。
2. **版本迁移（`onupgradeneeded`）手写极易写错，写错就丢用户已编译的数据** —— 而本项目的 schema 已经改过很多轮，未来还会改。
3. 节点 ↔ 事件线是**多对多**，需要 `multiEntry` 索引，原生写法冗长。

另外 PRD 2.8 已确定分库策略的**需求**（Canon 不可变、多条世界线物理隔离），但没定怎么落地。

## Decision

**采用 Dexie.js 作为 IndexedDB 封装层**，并采用如下分库策略：

```
westworld_canon                    ← Canon 层：所有书的编译产物（单库，记录带 bookId 字段）
westworld_state_{bookId}_{lineId}  ← 世界线库：每条世界线一个，物理隔离
```

> **修正（2026-10-03）**：早期版本写的是"每本书一个 Canon 库"，但业务数据里每条记录都带 `bookId`，
> 两者矛盾。改为**单个 Canon 库**：一本书的编译产物只存一份（靠 `bookId` 区分），
> 世界线才是真正需要物理隔离的层。

**Non-goals（明确不做）**：

- 不引入 SQLite / DuckDB / 图数据库（规模不够，见 PRD 2.7）
- 不做跨世界线的联合查询 UI（低频操作，需要时逐个开库即可）
- 不让业务代码直接使用原生 IndexedDB API

## Consequences

- **好的**：声明式迁移（`db.version(n).stores({...})`），schema 演进时不容易丢数据。
- **好的**：Dexie 是**薄封装** —— 底层仍是标准 IndexedDB，对象仓库与索引格式不变，必要时可降级回原生 API 而不丢数据。
- **好的**：Canon 是单库，一本书的编译产物只存一份；开第二条世界线时无需重新编译整本书。
- **好的**：一世界线一库 = 物理隔离，删档就是删库，不存在"漏过滤 `worldline_id` 导致串味"的 bug 类别。
- **坏的**：引入一个第三方依赖（约 80 KB）。
- **坏的**：跨世界线对比要同时打开多个 database（Canon 单库 + 每个世界线一个），代码更啰嗦。
- **风险**：Dexie 的 `multiEntry` 索引在半结构化数组数据上（节点 id 数组）行为需要实测确认。

## Implementation Plan

- **Affected paths**：`app/src/core/db/`（`dexie.ts`、各表定义、迁移）、`app/src/core/schema/`（Zod schema 作为表结构来源）
- **Dependencies**：`dexie`、`dexie-react-hooks`（UI 层响应式查询用）
- **Patterns to follow**：
  - 每个 database 一个模块：`app/src/core/db/canon.ts`、`app/src/core/db/worldline.ts`
  - 表结构集中声明，不要在业务代码里散落 `db.table(...)`
  - 所有写入走封装函数，不直接调 `table.put()`
  - 索引按 PRD 2.11 的清单建立（`by_chapter`、`by_time`、`by_event_line`(multiEntry)、`by_graph`、`by_source`、`by_target`、`by_type` 等）
- **Patterns to avoid**：
  - ❌ 不要在业务逻辑里直接写 `indexedDB.open()`
  - ❌ 不要用字符串拼接查询
  - ❌ 不要在没有迁移声明的情况下改表结构

### Verification

- [ ] 能创建 Canon 库并建出 PRD 2.11 清单里的全部对象仓库与索引
- [ ] `multiEntry` 索引生效：给一个节点写 `event_line_ids: ["L01","L02"]`，用 `where('by_event_line').equals('L02')` 能查到它
- [ ] 用一个模拟的 v1→v2 schema 变更验证迁移：旧数据保留，新索引可用
- [ ] 库名包含 `bookId` / `lineId`，同一本书的两条世界线互不可见
- [ ] 删除一条世界线后，Canon 库不受影响，可立即用同一 Canon 开新世界线
- [ ] 单本书的完整编译数据（10 万字级）写入后，重启应用数据完整

## Alternatives Considered

- **原生 IndexedDB**：零依赖，但迁移手写易错，且本项目 schema 会反复演进 —— 这个风险直接对应"丢用户几十分钟的编译成果"。
- **`idb`（Jake Archibald）**：提供了 Promise 化，但**没有解决迁移手写的问题**，等于只解决了一半痛点。
- **SQLite（WASM / sql.js）**：与已确定的"IndexedDB 存结构化数据"冲突；WASM 版的持久化还要自己落盘。
- **单库 + `worldline_id` 字段过滤**：跨线查询方便，但每个查询都必须记得带过滤，漏一次就串味 —— 这类 bug 靠自觉防守不可靠。
- **图数据库（Kuzu / Neo4j）**：见 PRD 2.7，本项目的图规模在内存里就能跑。

## More Information

**什么情况下该重新考虑**：

- 若单本书编译后的数据超过 **1 GB** → IndexedDB 可能吃力，需评估分片或迁移到 SQLite
- 若出现"必须跨世界线做复杂分析查询"的需求 → 考虑加 DuckDB WASM 只读层
- 若 Dexie 出现无法绕过的 bug → 降级到 `idb` 或原生 API（数据格式兼容，可平滑迁移）
