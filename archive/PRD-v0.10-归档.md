## M1.2 提取流水线（v4）

```
原书（长度无上限）
   │  导入阶段：正则分章 + 字数检测（>1 万字 → 101.1/101.2/101.3）
   ▼
[P1] 章节提取（唯一读原文的步骤）
   │  输入：一个章节（或一个子块）
   │  产出：① 本章事件节点（一段可多个）
   │        ② 本章人物快照
   │        ③ 本文的时间表达（可为空）
   ▼
[P2] 事件线聚合（滚动：1–100 → 80–180 → 170–270 …，固定 100 / 重叠 20）
   │  输入：窗口内的【节点流】，不是原文
   │  ① 串事件线（珍珠按颜色串起来）
   │  ② 顺便做节点去重合并
   │  ③ 给节点挂时间坐标
   │  断点处理：用时间坐标锁定区间 → 调工具回原文取证
   ▼
[P2'] 全书完成后的全局聚合（同样只读节点流）
   ▼
[P3] 网络化摆放 → 地图呈现（从左到右，有主干与分支）
       ★ 不做因果推理、不做伏笔回收、不打主线/支线标签
```

## M1.3 时间轴（用户定义的四指标模型）

**四指标**：

| # | 指标 | 谁赋 | 例 |
|---|------|------|----|
| 1 | **章节位置**（导入预处理后的章节名） | **代码** | 第 37 章 |
| 2 | **事件节点 ID** | **系统** | D1, D2, D3 … |
| 3 | **原文明确时间表述**（可为空） | **P1** | 4 月 3 日 / 洪武 14 年三月六日 / 亥时三刻 |
| 4 | **故事虚构时间坐标** | **P2**（推断） | 003 年 02 月 15 日 08:00 |

**虚构时间坐标的起点**：小说开始 = `00 年 00 月 00 日 00 小时`，按前后节点与原文进度推进。

**推断规则（用户原话）**：

- 显式锚点（"三日后""次年春""元妃省亲那年"）→ 坐标系原点，**尽量精确到小时**
- 锚点之间按相对表述推（"次日"→+1 天；"过了半月"→+15 天），**尽量精确到小时**
- 明显发生在同一天、甚至先后发生的，贴着最近锚点推，**尽量精确到小时**
- 完全没时间信息的 → 通过**前后事件的相对位置**推断（不再留空）

# M2 · 世界数据模型与状态

## M2.1 存储选型

**IndexedDB 与 JSON 并存**：

| 用途 | 存储 | 说明 |
|------|------|------|
| **正式数据**（运行时权威） | **IndexedDB** | 结构化存储，带索引 |
| **导出 / 备份 / 移植** | **JSON** | 用户可读、可迁移、可版本管理 |
| **小说原文正文** | **IndexedDB（按章分片 Blob）** | 小说一般几百 KB – 几十 MB，IndexedDB 毫无压力；**一章一条记录**，不塞成一个大 Blob |

**已采纳**：人物名等常用字段**反规范化**到节点 / 事件线上，避免 N+1 次读取。

## M2.4 叙事资产 Schema

### 事件节点（Node）

| 字段 | 谁生成 | 说明 |
|------|--------|------|
| `id` | **代码** | `C037-N02` = 第 37 章第 2 个节点 |
| `chapter_index` | **代码** | 37，用于排序与区间计算 |
| `chapter_name` | **代码** | 导入预处理后的章节名 |
| `name` | LLM | 事件名称（客观描述，不得是结论） |
| `summary` | LLM | 事件概述 |
| `time_text` | LLM 抽取 | 原文明确时间，**可空** |
| `time_coord` | **P2 推断** | 虚构时间坐标，**必须有**（P1 阶段为空） |
| `time_precision` | P2 | `explicit / inferred_hour / inferred_day / order_only` |
| `characters` | LLM | 涉及人物 |
| `node_status` | 运行时 | **未发生 / 已发生 / 已失效** |
| `quote` / `offset` | LLM + 代码 | 原文出处 |
| `created_by` | 代码 | `P1` / `P2`（P2 补建的节点要能区分） |

**注意**：`node_status`（未发生/已发生/已失效）与事件线的"是否结束"是**两个不同的状态**，命名必须区分开。

> **已失效**特指：玩家做出超出剧本的行为，导致该事件无法发生，从而开启新分支线。

### 事件线（EventLine）

| 字段 | 谁生成 | 说明 |
|------|--------|------|
| `id` | 系统 | 格式待定（暂定 `L01`） |
| `node_ids[]` | P2 | 涉及的事件节点 id |
| `chapters[]` | **代码** | 由 node_ids 自动生成 |
| `time_range` | **代码** | 由 node_ids 的时间坐标自动生成（最早 → 最晚） |
| `characters[]` | **代码** | 由 node_ids 的涉及人物自动汇总 |
| `cause` | LLM | **起因** |
| `process` | LLM | **经过** |
| `result` | LLM | **结果** |
| `line_status` | LLM | 是否已结束 |

**明确不做**：`gaps`（缺珍珠描述）不落库 —— 那是 P2 Agent 的**推理过程**，不是数据。P2 检查连贯性后**当场处理掉**（补节点 / 回原文 / 新建节点），处理完的产物就是更新后的节点列表与事件线。

### P2 的三项权限（新确认）

P2 检查事件线连贯性时，如果发现不连贯，可以：

1. 看该区间内是否还有其他节点可以补充进来
2. 直接去对应章节的原文里找补充
3. **新建事件节点**

> 由此产生的问题：P2 新建的节点 ID 如何分配（见 M2.10）

### 事件线之间怎么连（不违反"不做因果推理"）

由**代码自动推导**，不需要 LLM：

- 共享至少一个**节点** → `shares_node`
- 共享至少一个**主要人物 / 重要配角** → `shares_character`
- 时间区间重叠 → `temporal_overlap`

真正的因果边留到 M3 / M4，由运行时 Agent 产生。

## M2.6 多世界线隔离方案

**方案：Canon 单独一个库 + 每条世界线一个库**

```
westworld_canon_{bookId}           ← Canon 层（不可变，所有世界线共享，只编译一次）
westworld_wl_{bookId}_{lineId}     ← 该世界线的 State 层 + 账本 + 快照 + 图
```

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. 单库 + `worldline_id` 字段过滤 | 跨线对比方便 | 所有查询必须记得带过滤，容易串味 |
| **B. 一条世界线一个 database（推荐）** | **物理隔离，绝不串味；删档 = 删库**；Canon 只编译一次共享 | 跨线对比要开多个库（但那是低频操作） |

## M2.7 快照与回滚

**用户决定**：不覆盖，保存 **5 个回合的快照**（世界资产 + 叙事资产都存），方便回退回滚。

**待确认的工程细节**：

- **滚动窗口**：只保留最近 5 个快照（第 6 个到来时丢掉最旧的）
- **全量 vs 增量**：建议**全量快照**（简单可靠，几十 MB 对 IndexedDB 无压力，不会因为 patch 链断裂而回滚失败）
- **超过 5 轮后回不去怎么办**：建议 **5 个自动快照 + 手动永久存档点** 双轨

## M2.8 时间推进

**已确认**：时间**由玩家推动**。玩家做任何动作都会推进时间，也因此有可能错过事件。

**含义**：这是一个**回合制推进**的世界（不是实时流逝）。每次玩家行动 → Director 判定该动作消耗多少时间 → 世界时间前进 → 结算这段时间内应该发生的事。

→ 引出的必答项（记入 M3）：**动作 → 时间消耗** 如何判定。

## M2.10 图查询方案（已采纳）

**规模判断**：一本 100 万字小说约 5,000–20,000 个事件节点、500–2,000 个人物、几万条边 —— **内存里跑图毫无压力，不需要图数据库**。

```
① 持久层   IndexedDB
② 查询层   内存图 + 图算法（BFS / 最短路径 / 邻居 / 子图 / 中心性）
③ 接口层   图工具函数（给 Agent 调用）
```

**统一的边模型**（一张 `edges` 表管两种图）：

```json
{
  "id": "E_000123",
  "graph": "character",
  "source": "P001",
  "target": "P042",
  "type": "friendship",
  "label": "知己",
  "direction": "bidirectional",
  "evidence": ["C037-N02"],
  "created_at": "canon",
  "worldline_id": "wl_1"
}
```

**Agent 图工具**：`graph.neighbors` / `graph.path` / `graph.subgraph` / `graph.query` / `graph.stats`

**可视化**：底特律式从左到右流程图 → **React Flow**（首选）或 **Cytoscape.js + dagre**
（sigma.js / graphology 是力导向大图方案，不是流程图，不选）

**备选**：Kuzu WASM（Cypher，多带几 MB 依赖，MVP 不必要）
**排除**：Neo4j（要起服务，违背本地零配置）

## M2.13 收尾确认（M2 已封闭）

| # | 决定 |
|---|------|
| M2-Q12 | P2 补建的节点 ID：在缺失位置的原节点 ID 后追加编号。例：已有 `C3-N001`、`C3-N002`，在两者之间补一个 → **`C3-N0011`** |

**M2-Q12 的一个提醒（不影响功能，影响可读性）**：如果 `C3-N001` 后要补两个节点，会得到 `C3-N0011` 和 `C3-N0012`；再在这两者之间补，就变成 `C3-N00111`。长度会越滚越长。等价的替代写法是 `C3-N001.1` / `C3-N001.2`（同样能正确排序，但能看出层级）。**先用你的方案，遇到问题再换。**
