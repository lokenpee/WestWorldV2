# 事件驱动的可观测性：统一事件总线 + 完整日志窗口

## Context and Problem Statement

用户明确要求：**"完完整整的日志窗口必须做，用户必须能看到到底每一步在做什么"**。

这意味着这**不是**一个"事后查的日志表"，而是一套**实时的、事件驱动的可观测系统**：

- Agent 的 hook 要做好
- 事件要定义好
- 通过**监听（subscribe）**的方式报送任务进度
- 用户在界面上能看到每一步在做什么（模型调用、工具调用、重试、失败……）

同时仍需要回答成本问题：跑了上千次调用，花了多少钱、花在哪。

## 实现现状（2026-10-04）

| 项 | 状态 |
|----|------|
| 统一事件总线（`core/events/bus.ts`，监听器抛错不影响主流程） | ✅ 已实现 |
| 任务 / 章节级事件（`task:*`、`chapter:*`） | ✅ 已实现 |
| 实时日志窗口（`features/compile/CompilePanel.tsx`，订阅事件 → Zustand → UI） | ✅ 已实现 |
| 成本累计（每次调用累计 `cost`，随进度事件上报并显示） | ✅ 已实现 |
| Agent 层事件转发（PI 的 `agent_start` / `tool_execution_*`） | ⬜ 待接 Agent 时实现 |
| 事件**落库**（`compile_events`，导出与事后复盘用） | ⬜ 未实现（当前只在内存里） |
| 编译报告 / 成本报表 UI | ⬜ 未实现 |

> 结论：**"能看到每一步在做什么"这条已经成立**；"事后可复盘 + 可导出日志"还没做。
## Decision

### 1. 两层事件，汇入同一个事件总线

**第一层：Agent 事件（`pi-agent-core` 已提供，直接转发）**

PI 的 `AgentEvent` 已经定义了完整的事件类型，且提供 `Agent.subscribe()` 监听接口：

```typescript
export type AgentEvent =
  // Agent 生命周期
  | { type: "agent_start" }
  | { type: "agent_end"; messages: AgentMessage[] }
  // Turn 生命周期（一次 assistant 响应 + 它触发的工具调用）
  | { type: "turn_start" }
  | { type: "turn_end"; message: AgentMessage; toolResults: ToolResultMessage[] }
  // 消息生命周期
  | { type: "message_start"; message: AgentMessage }
  | { type: "message_update"; message: AgentMessage; assistantMessageEvent: AssistantMessageEvent }
  | { type: "message_end"; message: AgentMessage }
  // 工具执行生命周期
  | { type: "tool_execution_start"; toolCallId: string; toolName: string; args: any }
  | { type: "tool_execution_update"; toolCallId: string; toolName: string; args: any; partialResult: any }
  | { type: "tool_execution_end"; toolCallId: string; toolName: string; result: any; isError: boolean };
```

**我们不做任何重新发明 —— 直接 `subscribe()` 并转发到自己的总线。**

**第二层：任务级事件（我们在 pipeline 里发）**

PI 不知道"章节""窗口""编译任务"这些概念，所以要在 pipeline 层补：

| 事件 | 触发时机 |
|------|---------|
| `task_start` / `task_paused` / `task_resumed` / `task_cancelled` / `task_done` / `task_failed` | 任务状态机变化时 |
| `chapter_start` / `chapter_done` / `chapter_failed` | 每章处理的生命周期 |
| `chapter_retry` | 单章重试时（带重试次数与原因） |
| `window_start` / `window_done` | P2 每个 100 章窗口 |
| `cost_update` | 每次调用后累计费用变化 |
| `progress` | 已完成 / 失败 / 总数 / 预计剩余 |

### 2. 统一事件总线

```typescript
// app/src/core/events/bus.ts
interface EventBus {
  emit(event: AppEvent): void;
  on<T>(type: T['type'], handler: (e: T) => void): () => void;   // 返回取消订阅
  onAny(handler: (e: AppEvent) => void): () => void;             // 日志窗口用
}
```

**关键约束**：**监听器抛错不能影响主流程** —— `emit` 里逐个 try/catch，坏掉的监听器只打 console.warn 并继续。

**为什么用事件而不是回调参数**：日志窗口、进度条、费用显示、失败列表都要订阅同一批数据，事件总线让它们各自订阅而不互相耦合。

### 3. 完整日志窗口（UI）

**这是用户要求最明确的部分** —— 实时、逐条、可展开：

```
18:42:01  P1  ▶  第 37 章 开始
18:42:02  P1      → 调用 deepseek-flash（世界资产）3,200 tokens
18:42:11  P1      ← 返回 180 tokens · 8.4s · ¥0.0004
18:42:11  P1      → 调用 deepseek-flash（叙事资产）3,400 tokens
18:42:20  P1      ← 返回 220 tokens · 9.1s · ¥0.0005
18:42:20  P1  ✔  第 37 章 完成（人物 12 · 节点 8）
18:42:20  P1     累计 ¥0.42 · 437/1200 章 · 失败 2
```

**每条可展开看完整内容**：

- 模型调用 → 完整请求体（system / messages / tools）与完整响应体
- 工具调用 → 完整入参 + 完整返回值
- 错误 → `stopReason` / `errorMessage` / 重试次数

**过滤与搜索**：按阶段（P1/P2/P3）、按类型（模型 / 工具 / 错误）、按章节号过滤。

### 4. 持久化：完整窗口，有界存储

| | 决定 |
|---|---|
| 实时窗口 | **完整**（用户能看到每一步） |
| 持久化 | `compile_events` store，**环形缓冲**（默认保留最近 5000 条，可配） |
| 清空 | 提供"清空日志"按钮 |
| 导出备份 | **默认不含**事件日志（可勾选包含） |

**理由**：窗口要完整（可观测性），但存储必须有界（不然跑几本书就撑爆 IndexedDB）。

### 5. 费用统计

**数据来源**：`pi-ai` 内置 token 与 cost 计算（ADR-004 已确认），不需要自己维护价格表。

**累计与展示**：每次调用后 `cost_update`，实时显示 `累计 ¥X`。

**编译结束报告**：

```
编译完成
─────────────────────────
章节      1200 章（成功 1197 · 失败 3）
人物      843 个（主要 23 · 重要配角 71 · NPC 412 · 路人 337）
事件节点  18,432 个
事件线    276 条
耗时      52 分钟
费用      ¥9.87（3.6M input / 0.42M output tokens）

⚠️ 失败章节：第 88、402、911 章
   [重跑失败章节]

异常慢的章节：第 156 章（48 秒）
```

**失败数必须和完成数一样显眼** —— 因为 ADR-009 的策略是"失败就跳过"，跑完 ≠ 全部成功。

### 6. 绝不记录的东西

- **API Key**（无论何时，无论哪个日志）
- 这是唯一一条没有例外的脱敏规则

## Consequences

- **好的**：用户能看到每一步在做什么 —— 这是调 prompt、排查失败、理解费用的唯一有效手段。
- **好的**：直接复用 PI 的 `AgentEvent` + `subscribe()`，省掉自己设计 Agent 层可观测性的工作。
- **好的**：事件总线让日志窗口、进度条、费用显示、失败列表各自订阅，互不耦合。
- **坏的**：完整事件流的数据量很大（每次调用含完整请求响应），环形缓冲的容量需要按实际调优。
- **坏的**：事件日志包含小说正文 —— 导出备份时要显式排除（默认排除，可勾选包含）。
- **风险**：如果日志窗口渲染大量条目时没做虚拟滚动，会卡 UI（这是唯一需要性能注意的地方）。

## Implementation Plan

- **Affected paths**：`app/src/core/events/bus.ts`、`app/src/core/events/types.ts`、`app/src/core/observability/collector.ts`（订阅 PI 事件 + pipeline 事件，写入 store）、`app/src/core/db/`（`compile_events` store，索引 `by_book_stage` / `by_timestamp` / `by_chapter`）、`app/src/features/log-window/`（日志窗口 UI，**需虚拟滚动**）、`app/src/features/compile/`（进度）、`app/src/features/report/`（编译报告）
- **Dependencies**：无新增（虚拟滚动可用 `@tanstack/react-virtual`，约 5 KB）
- **Patterns to follow**：
  - PI Agent 的 `subscribe()` 在 `runAgent` 里统一挂载，把一个 PI 事件转成一个 `AppEvent` 后 `emit`
  - pipeline 的每个生命周期节点都 `emit`，不直接写 store
  - store 的写入由 `collector.ts` 单独订阅完成（UI 订阅与持久化订阅互不干扰）
  - 环形缓冲用一个 `count()` 检查 + 批量清理最旧记录
- **Patterns to avoid**：
  - ❌ 不要在 pipeline 里直接写日志 store（必须走事件）
  - ❌ 不要让某个监听器的异常中断编译
  - ❌ 不要在日志里记录 API Key
  - ❌ 不要在日志窗口里一次性渲染 5000 条（必须虚拟滚动）

### Verification

- [ ] 编译过程中，日志窗口能实时显示模型调用、工具调用、重试、失败
- [ ] 每条模型调用日志可展开看到完整请求体与响应体
- [ ] 日志窗口能按阶段 / 类型 / 章节号过滤
- [ ] 监听器抛错时，编译主流程不受影响（实测一次）
- [ ] 事件日志超过上限后，最旧的被清理（不无限增长）
- [ ] 累计费用与 `pi-ai` 返回的 usage 加总一致
- [ ] 全仓库搜索：日志相关代码里不存在 API Key 字段
- [ ] 导出备份的 JSON 里默认**不含**事件日志
- [ ] 日志窗口渲染 5000 条时，滚动不卡顿（虚拟滚动生效）

## Alternatives Considered

- **只用 console.log**：用户看不到，且无法事后查阅，与需求冲突。
- **只做"事后可查的日志表"，不做实时窗口**：用户明确要求"能看到每一步在做什么"，这是实时的需求。
- **自己设计 Agent 层事件**：PI 的 `AgentEvent` + `subscribe()` 已经覆盖 Agent/Turn/Message/Tool 四个生命周期，重新发明没有收益。
- **不做环形缓冲，全部保留**：跑几本书后 IndexedDB 会被撑爆。
- **默认关闭完整日志**：与用户"完完整整"的要求冲突。取舍改为"窗口完整，存储有界，导出默认排除"。

## More Information

**什么情况下该重新考虑**：

- 若日志窗口在高频事件下卡顿 → 引入事件节流（如模型 delta 事件合并），但**生命周期事件（start/end）不能节流**
- 若事件日志体积失控 → 降低环形缓冲上限，或只对失败的调用保留完整请求响应
- 若将来要加成本护栏（ADR-009 扩展点）→ 护栏的判断依据就是本 ADR 的 `cost_update` 累计值
