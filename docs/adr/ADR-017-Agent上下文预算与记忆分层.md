# Agent 上下文分层：常驻摘要 + 工具按需检索 + 超限分批

## Context and Problem Statement

P2 每 100 章要串一次事件线。100 章可能产生 **500–1,500 个事件节点**。如果把节点全塞进 prompt：

- 每个节点摘要约 50 tokens → 1,500 × 50 = **75,000 tokens**，已经接近多数模型的上限
- 加上已有事件线的摘要、工具定义、系统提示 → **必然超限**
- 而且 Agent 还需要多轮工具调用，上下文会**继续增长**

**这是本范围里最容易被低估的技术风险**：不控制上下文，P2 到第 300 章就会崩。

## Decision

### 1. 三层上下文，只有第一层进 prompt

```
① 常驻层（进 prompt）        任务说明 + 已有事件线的「摘要」+ 工具说明
② 检索层（按需，通过工具）   query_nodes / get_node_detail / read_original
③ 归档层（永不进 prompt）    完整节点数据，躺在 IndexedDB 里
```

**核心原则：不把节点全量塞进 prompt，而是告诉 Agent「你有工具，自己去查」。**

这是 ADR-007 设计「摘要模式 / 详情模式两级返回」的原因 —— 它们正是这一层的入口。

### 2. 摘要的具体粒度

| 对象 | 进 prompt 的内容 | 大约 tokens |
|------|----------------|-----------|
| 已有事件线 | 标题 + 时间区间 + 涉及人物 + `cause`/`result` 各一句 | ~80 / 条 |
| 本批节点 | **不进 prompt**，只告诉 Agent「本批有 N 个节点，范围是第 X–Y 章」 | ~20 |
| 节点详情 | 由 Agent 调 `query_nodes` 拉取（默认摘要模式，200 条上限） | 按需 |

### 3. 超限时自动分批

```
本窗口节点数 ≤ 阈值（默认 400）
   → 一次 Agent run
本窗口节点数 > 阈值
   → 按时序切成 N 批，每批单独 run
   → 后一批的输入里带上「前一批产出的事件线」（这就是已有的线，靠「能续就续」规则衔接）
```

**分批必须按时序切**，不能随机切 —— 否则同一件事的节点会被切到两批里，事件线就串不起来了。

### 4. 用 PI 的上下文压缩作为兜底

`pi-agent-core` / `pi-ai` 有上下文压缩机制（教程第 8/9 章）。**在分批策略之上再启用它作为兜底**：即使某次 run 的上下文增长超预期，也不会直接失败。

### 5. 预算与观测

- 每次 Agent run 记录 **输入 token 峰值**（进 ADR-010 的指标日志）
- 超过阈值时在日志窗口给出提示（"本批上下文接近上限，已自动分批"）

## Consequences

- **好的**：P2 从"跑几十章就崩"变成"能跑完全书"。
- **好的**：Agent 通过工具按需取数，比一次性喂全量**更省 token 也更准**（它只看相关的那部分）。
- **好的**：分批 + PI 压缩双保险，不会因为某一批异常就整个任务挂掉。
- **坏的**：Agent 需要多花几轮工具调用来"了解情况"，单次 run 的**延迟变高**（但 token 总量更低）。
- **坏的**：分批后，"跨批次的事件线闭合"依赖"能续就续"规则的正确执行 —— 规则失效会切出两条重复的线。
- **风险**：阈值（400）是拍脑袋定的，需要拿真实小说实测调整。

## Implementation Plan

- **Affected paths**：`app/src/core/agent/context.ts`（上下文组装与预算）、`app/src/core/pipeline/stages/p2.ts`（分批逻辑）、`app/src/core/agent/run.ts`（挂载 PI 的压缩）
- **Dependencies**：无新增
- **Patterns to follow**：
  - 上下文组装集中在一个函数 `buildAgentContext(batch, existingLines)`，可单测
  - 分批函数 `splitIntoBatches(nodes, threshold)` 是纯函数，可单测
  - 阈值放在配置里，不硬编码
- **Patterns to avoid**：
  - ❌ 不要把全部节点序列化进 prompt
  - ❌ 不要随机/按数量切批（必须按时序）
  - ❌ 不要在没有预算检查的情况下发起 Agent run

### Verification

- [ ] `splitIntoBatches` 是纯函数，单测覆盖：不超限（1 批）、刚好超限（2 批）、远超前限（N 批）
- [ ] 分批是**按时序**切的（断言每批的章节区间连续且不重叠）
- [ ] 用 1,000 个模拟节点跑 P2，不出现上下文超限错误
- [ ] 日志里能看到每次 run 的输入 token 峰值
- [ ] 全仓库搜索：`p2.ts` 里不存在"把全部节点 join 成字符串"的代码

## Alternatives Considered

- **全量塞进 prompt**：75,000+ tokens，接近上限，且工具调用后继续增长 → 必然失败。
- **只靠 PI 的上下文压缩**：压缩会**丢失细节**，而事件线串接恰恰依赖细节（谁和谁、什么时候）。应当先做分批，压缩只作兜底。
- **把窗口缩小到 20 章**：能规避问题，但事件线跨度常常超过 20 章，窗口太小会把同一条线切碎。
- **用向量检索替代工具查询**：Agent 需要的是**精确的结构化查询**（按章节区间、按人物、按事件线），不是语义相似度。

## More Information

**什么情况下该重新考虑**：

- 若实测阈值 400 仍会超限 → 降到 200，并观察事件线质量是否下降
- 若"跨批次事件线闭合"经常出错 → 考虑在批次之间显式传递未闭合线的摘要（目前是隐式依赖"能续就续"）
- 若延迟不可接受 → 评估把"节点摘要"也做成常驻（用更紧凑的格式，如 id + 一行）
