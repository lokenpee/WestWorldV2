# 导出为单个 `.wwv2` 压缩包，导入默认新建（不覆盖）

## Context and Problem Statement

ADR-001 定的是**纯浏览器 SPA**，数据存在 IndexedDB 里。这带来两个必须兜住的风险：

1. **浏览器可能清理数据** —— 用户清一次浏览数据，几十分钟的编译成果就没了
2. **换浏览器 / 换电脑带不走** —— IndexedDB 绑定在浏览器 profile 上

导出 / 导入是这两个风险的**唯一兜底**。

同时要解决格式问题：一本小说的结构化数据可能几 MB，原文可能几十 MB。**用单个 JSON 存原文需要 base64，体积膨胀 33%，而且要在内存里拼一个几十 MB 的字符串。**

另外 ADR-002 把数据拆成了**每本书一个 Canon 库** + 一个设置库，导出 / 导入必须跨这两个库操作：
记在书里的东西能导出，**书架记录与 API Key 都不能跟着书走**。

## Decision

### 1. 导出格式：单个 `.wwv2` 文件（本质是 zip）

```
测试书-20261004-1842.wwv2   (zip)
├── manifest.json                    ← 版本、书籍信息、导出时间、内容清单、校验和
├── data/
│   ├── book.json                    ← 书的元信息（不含 API Key）
│   ├── chapters.json                ← 章节元信息
│   ├── characterSnapshots.json      ← 人物快照（草稿层）
│   ├── locationSnapshots.json       ← 地点快照（草稿层）
│   ├── characters.json              ← 人物实体（入库后的资产包；没入库就是空数组）
│   ├── locations.json               ← 地点实体（同上）
│   ├── nodes.json                   ← 事件节点
│   ├── eventLines.json              ← 事件线
│   └── compileProgress.json         ← 编译进度（带着它才能在另一台机器上断点续跑）
├── chapters/
│   ├── 0001.txt                     ← 原文按章分片（不是一个大文件）
│   ├── 0101_1.txt                   ← 超长章切块用 下划线 + 序号
│   └── ...
└── （worldlines/ 留到 M8：世界线运行时数据）
```

**为什么分包而不是一个大 JSON**：

- 原文按章分片 → 解压 / 导入时可以**流式处理**，不需要一次性把全部内容读进内存
- 分片文件可读、可单独取出（用户想拿原文出来也方便）
- zip 压缩后体积明显小于 base64 的 JSON

> 快照与实体**都要导出**：快照是用户编辑的草稿，实体是已经入库的资产包。
> 只导出一份会丢东西 —— 重新入库需要快照，而已经入库的游戏包需要实体。

### 2. `manifest.json`

```json
{
  "format": "westworld-v2",
  "formatVersion": 1,
  "appVersion": "1.0.0",
  "exportedAt": "2026-10-04T18:42:00Z",
  "book": { "id": "bk_001", "title": "XXX", "author": "", "chapterCount": 1200 },
  "contents": [
    "book", "chapters",
    "characterSnapshots", "locationSnapshots",
    "characters", "locations",
    "nodes", "eventLines", "compileProgress"
  ],
  "excludes": ["apiKey", "eventLog"],
  "checksums": { "data/characters.json": "sha256:..." }
}
```

**`checksums`**：导入时校验完整性，防止文件损坏导致的半个世界。

### 3. 明确不含的内容

| 不导出 | 原因 |
|--------|------|
| **API Key** | 绝不导出（ADR-005）。它在**另一个库**（设置库）里，结构上就带不出来 |
| **事件日志**（`compile_events`） | 体积大且含正文；MVP 不导出 |
| **书架记录** | 属于**目标机器**的全局信息，导入时按新书重建（见第 4 条） |

> 编译进度**是导出的**（与早期版本不同）：用户在 A 机器上跑了 300 章、导出、换到 B 机器，
> 应该能接着跑第 301 章，而不是从头再来一遍（那是真金白银）。

### 4. 导入策略：默认**新建**，不覆盖

导入完成后**新建一本书**：

```
1. 在设置库里新建一条书架记录，拿到新的 bookId
2. 新建一个空库 westworld_canon_{新 bookId}
3. 把备份里的数据全部写进去（bookId 字段整体改写为新 id）
4. 原书原封不动
```

**理由**：导入的典型场景是"恢复备份"或"从另一台机器搬过来"，这时用户**不希望现有数据被覆盖**。

- 书名会加后缀「（导入）」，避免两本书重名分不清
- **不支持"合并导入"**（把两份备份揉成一份）—— 那需要重跑归并与事件线合并，MVP 不做

> **注意区分**：这里说的"合并"是指把**两份备份文件**揉成一份，与 P2/P3 的「世界资产合并」是完全不同的两件事 —— 后者照常做，见 PRD 2.2。

### 5. 版本兼容

| 情况 | 行为 |
|------|------|
| `formatVersion` 相同 | 直接导入 |
| `formatVersion` 更旧 | 走迁移（ADR-014），迁移后导入 |
| `formatVersion` 更新 | **拒绝**，提示"该备份由更新版本创建，请先升级应用" |

**校验顺序**（任何一步失败都要给出可读的失败原因，不能静默）：

```
1. 是不是合法 zip
2. manifest.json 存在且 format = "westworld-v2"
3. formatVersion 可处理
4. 逐个文件校验 checksum
5. 按 ADR-014 迁移
6. 新建书 + 新建库，在一个 Dexie 事务内写入
```

### 6. 技术选型

**用 `fflate`** 做 zip 读写：体积小（~10 KB）、浏览器可用、支持流式。

**Non-goals**：

- 不做云端同步
- 不做增量备份（每次导出都是全量）
- 不做自动定时备份（MVP 阶段手动导出即可）
- 不导出世界线运行时数据（M8 再说）

## Consequences

- **好的**：一个文件带走全部，换电脑 / 备份都是复制文件。
- **好的**：原文按章分片 + zip，避免了"几十 MB 字符串进内存"的问题。
- **好的**：导入默认新建（新书架记录 + 新库），不会误删用户现有数据。
- **好的**：checksum 能提前发现文件损坏，而不是导入到一半才发现。
- **好的**：编译进度跟着走，换机器能续跑，不重复花钱。
- **坏的**：多一个依赖（`fflate`）。
- **坏的**：导出大书（几十 MB）时会有几秒的压缩耗时，需要进度提示。
- **坏的**：拖家带口导出两份人物数据（快照 + 实体），备份体积略大（长篇小说几十 MB 量级，可接受）。
- **风险**：导入过程中断（关页面）会留下半本书。缓解：**在一个 Dexie 事务里写入**，失败自动回滚。

## Implementation Plan

- **Affected paths**：`app/src/core/export/export-book.ts`、`app/src/core/export/import-book.ts`、`app/src/core/export/manifest.ts`、`app/src/features/settings/`（导出 / 导入 UI 与进度）
- **Dependencies**：`fflate`
- **Patterns to follow**：
  - 导出：先收集各类数据 → 写 `data/*.json` → 写原文分片 → 算 checksum → 最后写 `manifest.json`
  - 导入：**先全部校验，再写库**（不要在流式写入过程中才发现文件坏了）
  - 导入必须**新建库**（`getCanonDb(新 bookId)`），不要往现有库写
  - 导出时在 UI 上明确标注"不含 API Key 与事件日志"
- **Patterns to avoid**：
  - ❌ 不要导出 API Key
  - ❌ 不要把原文拼成一个大字符串
  - ❌ 不要在导入时覆盖现有书的库

### Verification

- [x] 导出的 `.wwv2` 能被 7-Zip / 系统解压工具打开并看到预期结构
- [x] 导出文件里搜索不到 API Key（字符串 `sk-` 搜不到）
- [x] 每个文件都有 `sha256:` 校验和
- [x] 导入是**新建**：新书架记录 + 新库，原书原封不动
- [x] 手动改坏一个文件后导入，报"校验和不匹配"且**没有写入任何数据**
- [x] 导入一个 `formatVersion` 更高的文件，被明确拒绝并给出可读提示
- [x] 往返：导出再导入，章节数 / 人物数 / 地点数 / 节点数 / 事件线数一致
- [ ] 在一个全新的浏览器 profile 里导入，得到与导出前一致的数据
- [ ] 导入中断（强制关页面）后，IndexedDB 里没有半本书

## Alternatives Considered

- **单个 JSON 文件**：原文要 base64，体积膨胀 33%，且几十 MB 字符串进内存有风险。
- **多个散装文件**：用户容易漏拷、易损坏，不是"一个文件带走"的体验。
- **导入时覆盖同名书**：风险大（用户可能误操作），且与"恢复备份"的语义不符。
- **只导出实体、不导出快照**：体积小一点，但用户换机器后**没法继续编辑草稿**（改不了人、合并不了），只能玩不能改 —— 用户明确要求"入库前能随便改"。
- **支持"合并导入"（把两份备份文件揉成一份）**：需要重新跑归并与事件线合并，复杂度高，MVP 不做。
- **自动定时导出到本地文件夹**：浏览器做不到无感写文件（除非用 File System Access API），且 MVP 不需要。

## More Information

**什么情况下该重新考虑**：

- 若用户反馈"想定时自动备份" → 评估 File System Access API（用户授权一个目录，可无感写入）
- 若将来需要"合并两份数据" → 本质是把 P3 的世界资产合并流程跑一遍，可以复用同一套 merge
- 若备份体积过大（>200 MB）→ 考虑原文单独导出、结构化数据与原文分离
- 若 M8 的世界线数据也要跟着走 → `worldlines/` 目录与 `formatVersion` 一起升级
