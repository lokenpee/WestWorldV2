# 采用 `@earendil-works/pi-ai` 作为模型调用层，不再自建 Provider

## Context and Problem Statement

链路里不同步骤对模型的要求完全不同：

| 步骤 | 调用量 | 要求 |
|------|--------|------|
| **P1 章节提取** | 最大（一本书几百到上千次 × 2） | 结构化输出必须稳定；可用便宜模型 |
| **P2 事件线聚合** | 小（每 100 章一次） | 长上下文与推理；用强模型 |
| **P3 全书收尾** | 极小 | 长上下文 |

**结论：一定会换模型、一定会混用模型。**

原方案（自建一个薄的 `LLMProvider` 接口）能解决"可替换"，但**换不来**下面这些必须自己写的东西：

- 各家的结构化输出 / function calling 差异
- 流式响应与中断（`AbortSignal`）
- token 与成本的统计
- 凭据管理

而 **PI（`@earendil-works/pi-ai`）** 已经把这些做完了。

## Decision

**采用 `@earendil-works/pi-ai` 作为模型调用层**，不再自建 Provider 抽象。

**已核实的能力**（2026-10-03）：

| 能力 | 状态 |
|------|------|
| 浏览器可用 | ✅ README 有专门的 Browser Usage 章节 |
| DeepSeek | ✅ 在官方 provider 列表里 |
| 统一多供应商 | ✅ 30+ 家 |
| 工具调用（function calling） | ✅ 内置 |
| 结构化输出（strict JSON Schema） | ✅ `constrainedSampling: { strict: 'prefer' }` |
| token / 成本跟踪 | ✅ 内置 |
| 中断 | ✅ 支持 `AbortSignal` |
| 凭据存储 | ✅ `CredentialStore` 接口，可注入自定义持久化 |

**我们的约定（PI 之上必须遵守）**：

1. **配置驱动**：模型名、base URL、Key 全部走配置，**不硬编码在调用点**
2. **Tree-shaking**：只 import 用到的 provider 子路径（`@earendil-works/pi-ai/providers/deepseek`），**不要 import `providers/all`**（会把所有 SDK 打进包）
3. **CredentialStore 用 IndexedDB 实现**（见 ADR-005）
4. **所有模型输出过 TypeBox 校验**（见 ADR-003），不合法则带错误重试
5. **每次调用记录 token 用量**（PI 已提供，见 ADR-010）

**Non-goals（明确不做）**：

- 不自建 Provider 抽象层（PI 就是那个抽象层）
- 不引入 Vercel AI SDK / LangChain
- 不在调用点直接 `import OpenAI from 'openai'`
- 不支持 Bedrock 与 OAuth 登录（浏览器不支持，且我们不需要）

## Consequences

- **好的**：省掉整个 Provider 抽象层的开发与维护。
- **好的**：换模型 / 加供应商是配置问题，不是代码问题。
- **好的**：token 与成本统计现成，ADR-010 的可观测性省一半工作量。
- **好的**：`CredentialStore` 的接口契约正好对上 ADR-005 的"Key 存 IndexedDB"。
- **坏的**：引入 `pi-ai` 及其 provider SDK 依赖，**打包体积会明显增大**（需要按需 import + 代码分割）。
- **坏的**：接受 PI 的 API 形态与升级节奏；它升 major 时我们可能要跟着改。
- ~~**风险**：`pi-ai` 声明 `engines: node >= 22`（那是给 CLI 的）。浏览器构建路径需要实测验证~~ → **已于 2026-10-03 实测通过**（见 Spike 报告）。唯一警告是 `provider-env.js` 里的 `require("node:fs")`（Bun 专属分支，浏览器不会执行到）。

## Implementation Plan

- **Affected paths**：`app/src/core/llm/models.ts`（`createModels()` 初始化与 provider 注册）、`app/src/core/llm/credentials.ts`（IndexedDB 版 `CredentialStore`）、`app/src/core/config/`（模型配置）
- **Dependencies**：`@earendil-works/pi-ai`、`@sinclair/typebox`
- **Patterns to follow**：
  - 只注册用到的 provider：

    ```typescript
    import { createModels } from '@earendil-works/pi-ai/models';
    import { deepseekProvider } from '@earendil-works/pi-ai/providers/deepseek';

    const models = createModels({ credentials: indexedDbCredentialStore });
    models.setProvider(deepseekProvider());
    ```

  - 模型名从配置读，不写死在调用点
  - 所有调用走统一封装，集中处理重试与用量记录
- **Patterns to avoid**：
  - ❌ `import { ... } from '@earendil-works/pi-ai/providers/all'`
  - ❌ 在调用点硬编码 base URL / 模型名 / Key
  - ❌ 引入第二套模型调用库（Vercel AI SDK / LangChain）

### Verification

- [x] ✅ **浏览器冒烟测试（2026-10-03 已验证通过）**：Vite 构建 + headless Chrome 加载 + 真实发起对 `api.deepseek.com` 的请求，拿到服务端返回的 401 + request_id。**DeepSeek 允许浏览器直连，无 CORS 问题。** 详见 `docs/spikes/2026-10-03-pi-ai-browser-verification.md`
- [ ] 构建产物中**不包含**未使用的 provider SDK（用 bundle 分析确认）
- [ ] 切换配置文件里的模型名，无需改代码即可换模型
- [ ] 传结构化输出 schema 后，返回结果能通过 TypeBox 校验
- [ ] 每次调用后能拿到 token 用量（input / output）
- [ ] 全仓库搜索：`app/src/` 下不存在 `from 'openai'` / `from '@anthropic-ai/sdk'` 的直接 import

## Alternatives Considered

- **自建薄的 `LLMProvider` 接口（原方案，已否决）**：能解决可替换性，但结构化输出差异、流式、中断、用量统计都要自己写；且 PI 已经做完了这些并且支持浏览器。
- **Vercel AI SDK**：成熟、跨供应商，但与本项目的"薄接口"取向不同；引入后同样要与 PI 的功能重叠。
- **直接写死某家 SDK**：换模型要改一片；且 P1/P2 对模型的要求差异明显，一开始就需要能切换。
- **提示词要求"只输出 JSON" + 自己解析**：解析失败率高且静默失败，与 ADR-003 的初衷冲突。

## 验证结果（2026-10-03）

| 验证项 | 结果 |
|--------|------|
| 浏览器 import | ✅ |
| `createModels()` + `deepseekProvider()` | ✅ |
| 模型目录 | ✅ `deepseek-flash` / `deepseek-v4-pro` |
| **真实网络请求** | ✅ 打到 `api.deepseek.com/chat/completions`，服务端返回 401（假 key，符合预期） |
| **CORS** | ✅ 无拦截 —— 浏览器可直连 DeepSeek |
| 代码分割 | ✅ OpenAI SDK（312 KB）被切成懒加载 chunk |

**⚠️ 验证中发现并必须遵守的实现约定**：

> `models.complete()` **失败时不抛异常**，而是返回 `stopReason: "error"` 并附带 `errorMessage`。
> **不能用 try/catch 判成败**，必须检查 `res.stopReason`。否则所有模型调用失败都会静默通过。

## More Information

**什么情况下该重新考虑**：

- 若浏览器构建路径实测**不可行** → 回到自建薄 Provider，或重新评估运行形态（ADR-001）
- 若打包体积不可接受 → 评估按 provider 做动态 import / 独立 chunk
- 若 PI 升级到不兼容版本 → 锁定版本，评估迁移成本

相关：ADR-001（浏览器形态）、ADR-003（TypeBox）、ADR-005（Key 存储）、ADR-006（Agent 运行时）、ADR-010（可观测性）
