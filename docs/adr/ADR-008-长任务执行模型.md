# 长任务执行模型：DOM-free 的 pipeline + 主线程调度 + IndexedDB 断点续跑

## Context and Problem Statement

编译一本 100 万字小说可能要跑几十分钟到几小时，涉及：

- **P1**：上千个章节任务（每章 2 次模型调用），已定并发 3
- **P2**：每 100 章一次的滚动 run（**先合并世界资产快照，再串联事件线**，顺序不能颠倒）
- **P3**：全书收尾

必须解决四个具体问题：

1. **任务跑在哪**：主线程会卡 UI 吗？要不要 Web Worker？
2. **进度存哪**：用户关掉标签页，下次能不能接着跑？（用户已定：中断，下次从断点续跑）
3. **怎么取消**：用户按下取消，正在跑的章节怎么办？（用户已定：保留已完成章节）
4. **状态怎么表达**：一个编译任务有哪些状态、怎么持久化

## Decision

### 1. Pipeline 必须 DOM-free，但 MVP 跑在主线程

```
app/src/core/pipeline/     ← 长任务逻辑，禁止 import React / DOM API
app/src/features/          ← UI，只负责发起任务、订阅进度
```

**MVP 跑在主线程**，理由：

- 主要开销是**网络请求**（P1 每章 2 次调用，每次 10–30 秒），fetch 是异步的，不阻塞 UI
- 真正的 CPU 开销（JSON 解析、IndexedDB 写入）很小
- 少一层 Worker 的消息传递与调试复杂度

**但把 pipeline 写成 DOM-free 是硬约束** —— 这样将来如果实测 UI 确实卡顿，可以把整个 pipeline 搬进 Worker，搬迁成本极低（只需加一层薄消息层）。

**Non-goals**：

- MVP 不引入 Web Worker
- 不做后台常驻（浏览器做不到，且 ADR-001 已接受这个限制）
- 不做多本书并行编译（同时只跑一个编译任务）

**例外：入库（`publishCanon`）不是长任务。** 它**不调模型**、纯代码、毫秒到秒级，
一次事务写完，不需要断点续跑 / 暂停 / 取消。所以它不进 pipeline 的阶段编排，
是一个普通函数调用（见 ADR-018）。

### 2. 任务状态机

```
idle
  ↓ start
running ──cancel──→ cancelling ──→ cancelled
  ↑   ↓                                   （已完成的章节保留）
  └─ paused（✅ 已确认需要）──resume──→ running
  ↓ 全部完成
completed

running ──不可恢复错误──→ failed
```

**状态语义**：

| 状态 | 含义 | 能否恢复 |
|------|------|---------|
| `running` | 正在跑 | — |
| `paused` | 用户主动暂停（✅ 已确认） | ✅ 可继续 |
| `cancelling` | 已请求取消，在等在途请求结束 | — |
| `cancelled` | 已取消，**已完成的章节保留** | ✅ 可再次启动，从未完成处继续 |
| `failed` | 不可恢复错误（如 401） | ✅ 修正原因后可重试 |
| `completed` | 该阶段全部完成 | — |

### 3. 进度持久化与断点续跑

**存哪**：`compileProgress` store（在**这本书自己的** Canon 库里，见 PRD 2.11）

```json
{
  "bookId": "bk_001",
  "stage": "P1",
  "completedChapters": ["1", "2", "3", "5"],
  "failedChapters": ["4"],
  "totalChapters": 1200,
  "lastWindowIndex": 2,
  "updatedAt": "2026-10-03T10:00:00Z",
  "status": "running"
}
```

**续跑判定**：

```
待处理章节 = 全部章节 − completedChapters − failedChapters
```

**写入时机**：**每章完成立即写**（不是批量写）—— 这是断点续跑能成立的前提。

**P2 的进度**：用 `lastWindowIndex` 记录已完成的窗口序号（0 = 1–100，1 = 80–180，…）。

**页面重开后的行为（已确认）**：

> 检测到未完成的编译任务时，**弹窗询问用户是否继续**，**不自动继续**。
> 理由：继续会消耗用户的钱，必须得到明确确认。

弹窗内容要具体：

```
检测到未完成的编译任务
《XXX》· P1 提取 · 已完成 437 / 1200 章（上次中断于 2026-10-03 18:42）
继续的话还需要处理 763 章，预计花费 ¥6.2
[继续]  [稍后]  [放弃这次编译]
```

### 4. 并发调度

```
任务池：1200 个章节任务
并发度：3（可配，见 ADR-009）
调度：谁先空出来就领下一个未完成的章节
```

**实现上就是一个 promise pool**，不需要引入任务队列库：

```typescript
async function runPool<T>(items: T[], concurrency: number, worker: (item: T) => Promise<void>, signal: AbortSignal) {
  let cursor = 0;
  const runners = Array.from({ length: concurrency }, async () => {
    while (cursor < items.length && !signal.aborted) {
      await worker(items[cursor++]);
    }
  });
  await Promise.all(runners);
}
```

**并发不影响正确性**：每个章节任务写的是自己那条记录（按 `chapter_index`），互不冲突。

### 5. 暂停与取消

**暂停（`paused`）** 与取消的区别：**保留待办列表**，恢复时不用重新计算"哪些没做完"。

- 暂停时：停止领新任务，等在途请求结束，未完成的章节保留在待办里
- 恢复时：从待办继续，已完成的不重跑

### 6. 取消

- 一个 `AbortController` per 编译任务
- 取消时：
  1. 立刻停止从池里领新任务（`signal.aborted`）
  2. 对在途的模型请求调 `abort()`
  3. **已完成的章节保留**
  4. 在途但未完成的章节：**丢弃，标记为未完成**（下次会重跑）
- 取消可能要等几秒（等在途请求真正结束），UI 上显示 `cancelling` 状态

### 7. 失败章节

单章重试耗尽后：**标记失败、跳过、继续下一章**（⚠️ 待确认是否改成中止）

编译结束后给出失败章节列表，用户可单独重跑。

## Consequences

- **好的**：DOM-free 的 pipeline 让"将来搬进 Worker"只是一个可选优化，不是重构。
- **好的**：每章完成即落库，断点续跑几乎零成本实现。
- **好的**：promise pool 只有十几行，不需要引入任务队列依赖。
- **坏的**：主线程跑长任务时，如果 pipeline 里不小心写了同步的重活（比如正则在大文本上跑），仍然会卡 UI —— 需要靠"DOM-free + 避免同步重活"的纪律来防。
- **风险**：并发 3 个章节同时写 IndexedDB，需要确认 Dexie 的写入不会互相锁住（理论上不会，因为是不同记录）。

## Implementation Plan

- **Affected paths**：`app/src/core/pipeline/runner.ts`（promise pool + 状态机）、`app/src/core/pipeline/progress.ts`（进度读写）、`app/src/core/pipeline/stages/p1.ts` / `p2.ts` / `p3.ts`、`app/src/features/compile/`（进度 UI 与取消按钮）
- **Dependencies**：无新增
- **Patterns to follow**：
  - 每个阶段导出一个 `runP1(ctx, signal)` 之类的函数，接收 `AbortSignal`
  - 进度写入集中在 `progress.ts`，各阶段不自己写
  - 所有 pipeline 代码不 import React、不碰 `window` / `document`
- **Patterns to avoid**：
  - ❌ 不要在 pipeline 里做同步的重活（大文本正则、大 JSON 深拷贝）
  - ❌ 不要在 React 组件里直接跑 pipeline 循环
  - ❌ 不要批量写进度（必须每章写）

### Verification

- [ ] 编译到第 300 章时强制关闭标签页，重开能从未完成处继续，不重复已完成章节
- [ ] 取消后已完成的章节数据完整，未完成的章节在下次启动时被重新处理
- [ ] 并发 3 时不会写坏数据（章节数与内容与串行结果一致）
- [ ] 全仓库搜索：`app/src/core/pipeline/` 下不存在 `import React` / `document.` / `window.`
- [ ] 取消请求后 5 秒内状态变为 cancelled`r
- [ ] 暂停后恢复，不重复处理已完成的章节
- [ ] 重开页面时**弹窗询问**，不自动继续；选「稍后」后进度保留

## Alternatives Considered

- **Web Worker**：能彻底避免卡 UI，但 MVP 阶段的网络开销不阻塞主线程，引入 Worker 只增加调试复杂度。**保留为将来的优化路径**（因为 pipeline 是 DOM-free 的，搬迁成本低）。
- **引入任务队列库（如 BullMQ / p-queue）**：`p-queue` 只有几 KB 且成熟，但我们的需求就是一个 promise pool，自己写十几行更可控。
- **批量写进度（每 10 章写一次）**：性能略好，但崩在第 9 章时会丢 9 章的成果 —— 对"跑几十分钟"的任务不可接受。

## More Information

**什么情况下该重新考虑**：

- 若实测 UI 明显卡顿 → 把 pipeline 搬进 Worker（架构已为此预留）
- 若并发写入出现锁冲突 → 引入写入队列
- ~~若需要"暂停"功能~~ → 已加入状态机
