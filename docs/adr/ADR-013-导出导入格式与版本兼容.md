# 导出为单个 `.wwv2` 压缩包，导入默认新建（不覆盖）

## Context and Problem Statement

ADR-001 定的是**纯浏览器 SPA**，数据存在 IndexedDB 里。这带来两个必须兜住的风险：

1. **浏览器可能清理数据** —— 用户清一次浏览数据，几十分钟的编译成果就没了
2. **换浏览器 / 换电脑带不走** —— IndexedDB 绑定在浏览器 profile 上

导出 / 导入是这两个风险的**唯一兜底**。

同时要解决格式问题：一本小说的结构化数据可能几 MB，原文可能几十 MB。**用单个 JSON 存原文需要 base64，体积膨胀 33%，而且要在内存里拼一个几十 MB 的字符串。**

## Decision

### 1. 导出格式：单个 `.wwv2` 文件（本质是 zip）

```
backup-20261003-1842.wwv2   (zip)
├── manifest.json           ← 版本、书籍信息、导出时间、内容清单
├── data/
│   ├── characters.json
│   ├── locations.json
│   ├── nodes.json
│   ├── event_lines.json
│   ├── edges.json
│   └── timeline.json
├── chapters/
│   ├── 0001.txt            ← 原文按章分片（不是一个大文件）
│   ├── 0002.txt
│   └── ...
└── worldlines/
    └── wl_1/
        ├── world_state.json
        ├── entity_state.json
        └── snapshots.json
```

**为什么分包而不是一个大 JSON**：

- 原文按章分片 → 解压 / 导入时可以**流式处理**，不需要一次性把全部内容读进内存
- 分片文件可读、可单独取出（用户想拿原文出来也方便）
- zip 压缩后体积明显小于 base64 的 JSON

### 2. `manifest.json`

```json
{
  "format": "westworld-v2",
  "formatVersion": 1,
  "appVersion": "0.1.0",
  "exportedAt": "2026-10-03T18:42:00Z",
  "book": { "id": "bk_001", "title": "XXX", "author": "", "chapterCount": 1200 },
  "contents": ["characters", "locations", "nodes", "event_lines", "edges", "timeline", "chapters", "worldlines"],
  "excludes": ["apiKey", "eventLog"],
  "checksums": { "data/characters.json": "sha256:..." }
}
```

**`checksums`**：导入时校验完整性，防止文件损坏导致的半个世界。

### 3. 明确不含的内容

| 不导出 | 原因 |
|--------|------|
| **API Key** | 绝不导出（ADR-005） |
| **事件日志**（`compile_events`） | 体积大且含正文；**默认排除**，导出时可勾选包含 |
| 编译进度（`compile_progress`） | 属于临时状态，恢复后重新计算即可 |

### 4. 导入策略：默认**新建**，不覆盖

导入完成后**新建一本书**，而不是覆盖现有的同名书。

**理由**：导入的典型场景是"恢复备份"或"从另一台机器搬过来"，这时用户**不希望现有数据被覆盖**。

如果检测到同名书 → 提示：
```
已存在书籍《XXX》
[新建一份副本]  [取消]
```
（**注意区分**：这里说的"合并"是指把**两份备份文件**揉成一份，与 P2/P3 的「世界资产合并」是完全不同的两件事 —— 后者照常做，见 PRD 2.2）

### 5. 版本兼容

| 情况 | 行为 |
|------|------|
| `formatVersion` 相同 | 直接导入 |
| `formatVersion` 更旧 | 走迁移（ADR-014），迁移后导入 |
| `formatVersion` 更新 | **拒绝**，提示"该备份由更新版本创建，请先升级应用" |

**校验顺序**（任何一步失败都要给出可读的失败原因，不能静默）：

```
1. 是不是合法 zip
2. manifest.json 存在且 format = "westworld-v2"
3. formatVersion 可处理
4. 逐个文件校验 checksum
5. 按 ADR-014 迁移
6. 写入 IndexedDB（一个事务内）
```

### 6. 技术选型

**用 `fflate`** 做 zip 读写：体积小（~10 KB）、浏览器可用、支持流式。

**Non-goals**：

- 不做云端同步
- 不做增量备份（每次导出都是全量）
- 不做自动定时备份（MVP 阶段手动导出即可）

## Consequences

- **好的**：一个文件带走全部，换电脑 / 备份都是复制文件。
- **好的**：原文按章分片 + zip，避免了"几十 MB 字符串进内存"的问题。
- **好的**：导入默认新建，不会误删用户现有数据。
- **好的**：checksum 能提前发现文件损坏，而不是导入到一半才发现。
- **坏的**：多一个依赖（`fflate`）。
- **坏的**：导出大书（几十 MB）时会有几秒的压缩耗时，需要进度提示。
- **风险**：导入过程中断（关页面）会留下半本书。缓解：**在一个 Dexie 事务里写入**，失败自动回滚。

## Implementation Plan

- **Affected paths**：`app/src/core/export/export-book.ts`、`app/src/core/export/import-book.ts`、`app/src/core/export/manifest.ts`、`app/src/features/backup/`（导出 / 导入 UI 与进度）
- **Dependencies**：`fflate`
- **Patterns to follow**：
  - 导出：先写 manifest（含 checksum）→ 再逐类数据 → 最后原文分片
  - 导入：**先全部校验，再写库**（不要在流式写入过程中才发现文件坏了）
  - 整体写入放在一个 Dexie 事务里
  - 导出时在 UI 上明确标注"不含 API Key 与事件日志"
- **Patterns to avoid**：
  - ❌ 不要导出 API Key
  - ❌ 不要把原文拼成一个大字符串
  - ❌ 不要在索引库外面记录"导入到一半"的临时状态

### Verification

- [ ] 导出的 `.wwv2` 能被 7-Zip / 系统解压工具打开并看到预期结构
- [ ] 导出文件里搜索不到 API Key
- [ ] 导出文件里默认不含事件日志
- [ ] 在一个全新的浏览器 profile 里导入，得到与导出前一致的数据（人物数 / 节点数 / 事件线数 / 原文章节数全部相等）
- [ ] 手动改坏一个文件后导入，报"checksum 校验失败"且**没有写入任何数据**
- [ ] 导入中断（强制关页面）后，IndexedDB 里没有半本书
- [ ] 导入一个 `formatVersion` 更高的文件，被明确拒绝并给出可读提示

## Alternatives Considered

- **单个 JSON 文件**：原文要 base64，体积膨胀 33%，且几十 MB 字符串进内存有风险。
- **多个散装文件**：用户容易漏拷、易损坏，不是"一个文件带走"的体验。
- **导入时覆盖同名书**：风险大（用户可能误操作），且与"恢复备份"的语义不符。
- **支持"合并导入"（把两份备份文件揉成一份）**：这与 P2/P3 的「世界资产合并」不是一回事。后者是同一本书内部的归并（照常做）；前者是把两份独立备份的数据合成一份，需要重新跑归并与事件线合并，复杂度高，MVP 不做。
- **自动定时导出到本地文件夹**：浏览器做不到无感写文件（除非用 File System Access API），且 MVP 不需要。

## More Information

**什么情况下该重新考虑**：

- 若用户反馈"想定时自动备份" → 评估 File System Access API（用户授权一个目录，可无感写入）
- 若将来需要"合并两份数据" → 本质是把 P3 的世界资产合并流程跑一遍，可以复用 ADR-008 的 pipeline
- 若备份体积过大（>200 MB）→ 考虑原文单独导出、结构化数据与原文分离

相关：ADR-001（纯浏览器导致的数据风险）、ADR-005（API Key 不导出）、ADR-014（迁移）
